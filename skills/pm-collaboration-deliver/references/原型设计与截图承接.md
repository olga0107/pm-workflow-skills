## 1. 能力分层

原型能力不是“把 PRD 画成几个手机框”，而是一条从事实到阅读结果的编译链：

| 层 | 回答的问题 | 产物 |
|---|---|---|
| 输入证据层 | 哪些是正式产品事实，哪些只是现状截图、视觉参考或推断 | 证据清单、来源角色、缺口 |
| 设计语义层 | 用户在哪个页面、看到什么、能做什么、动作后发生什么 | Page / Surface、IA、State、Action、Transition |
| 视觉执行层 | 用什么页面结构、关键帧、标注和布局让逻辑一眼可见 | 页面地图、标注截图、状态对比、故事板或低保真 |
| 交付验证层 | 资产放入传统 PRD 或目标平台后是否仍清楚、同源、无错位 | 正文装配、渲染检查、独立阅读结果 |

Skill 工程化横跨四层：路由和参考负责判断，结构化计划负责交接，渲染器负责重复机械工作，检查器负责阻止断链。工具不能替代产品判断。

## 2. 上游输入充分度

`pm-prd-write` 在复杂界面需求中应交付 Page / Surface、IA / Section、用户可见状态、操作、迁移、异常恢复和验收来源。它定义产品交互语义，不保证最终视觉稿、坐标或设计系统细节。先在两个独立维度判断输入：

### 2.1 产品语义充分度

| 状态 | 已知内容 | 允许输出 | 不允许输出 |
|---|---|---|---|
| `interaction_complete` | 页面、状态、动作、迁移和恢复均可追溯 | 完整状态模型、聚焦故事板、状态对比、低保真结构示意 | 新增业务条件或恢复规则 |
| `structure_complete` | 页面目的、信息区、可见内容和主要动作明确，但迁移不完整 | 页面地图、单状态低保真、局部结构对照 | 声称完整的交互故事板或全景 |
| `partial` | 只有页面名、功能摘要或零散界面描述 | 缺口清单、现状截图标注、已有资产索引 | 目标页面和连续交互 |
| `insufficient` | 无法确定页面目的、主要内容或动作结果 | 返回上游补齐 | 任何看似确定的目标原型 |

不能因为 AI 能推断常见模式，就把 `partial` 升级为完整设计。会改变入口、信息、操作、状态、结果或恢复的缺口必须回到上游。

### 2.2 视觉上下文充分度

| 状态 | 默认策略 |
|---|---|
| `confirmed_design` | 复用具体 Frame / 组件，优先做局部标注、差异说明或增量修改 |
| `existing_ui` | 提取现状结构和约束；目标方案仍由正式 PRD 决定 |
| `reference_only` | 只借鉴可说明的视觉模式，不默认沿用结构、文案和交互 |
| `declared_unverified` | 正式 PRD 声明资产存在，但文件本轮不可访问或禁止读取；记录声明与限制，不把它当作已查看资产，按 `plan_only` 或明确标注的低保真策略继续 |
| `none` | 使用明确标注的低保真结构示意，不伪装成最终设计 |

产品语义充分不等于视觉上下文充分；有截图也不等于交互规则充分。两个维度必须分别记录。

`declared_unverified` 不等于 `none`：前者保留“上游声明已有设计/原型”的事实，避免误写为没有资产；但在实际读取前，不得选择 `reuse_confirmed` 或声称完成设计一致性验证。

## 3. 设计权限与资产策略

对每个受影响 Surface 选择一种策略，并写明来源和理由：

- `reuse_confirmed`：直接复用已确认设计，不重画整页；
- `adapt_existing`：沿用现有页面壳、组件和信息层级，只表达本次变化；
- `reference_only`：截图或案例仅作观察证据，目标原型从正式 PRD 编译；
- `low_fidelity_new`：没有可复用资产但语义足够时，生成结构示意；
- `plan_only`：输入不足，只输出需要补齐的设计问题。

已存在正式设计时，重画必须说明为什么复用、标注或增量修改不能回答评审问题。局部变化默认标注局部，不为了“看起来完整”重新设计整页。

只要本期改变页面结构、主操作、可见反馈或关键状态，视觉就属于需求解释的一部分，而不是装饰项：

- 输入包含可访问截图或设计稿时，至少在对应详情中复用一处相关视觉，并明确它是现状、已确认设计还是参考；
- 输入没有视觉上下文但产品语义达到 `structure_complete` 或 `interaction_complete` 时，至少为核心变化页面输出一张低保真结构示意；
- 只有纯文案、字段、不可见规则、或图无法比短文/小表更清楚时才可以不生成页面视觉。

“源文档有图但正文未使用”和“新增核心页面但只有流程框图”都视为原型承接未完成。

设计语义层可以补全的是：信息分组、阅读优先级、主次操作关系、反馈邻近性、关键状态差异和故事板关键帧选择。不得补全的是：上游未确认的业务规则、入口、权限、状态结果和恢复路径。

## 4. 截图证据工作流

截图进入流程后，先把它当作可观察证据，不把像素当作产品规则。

### 4.1 分类与登记

为每张图记录：

- 角色：`current_ui`、`confirmed_design` 或 `visual_reference`；
- 覆盖的页面、版本、端和状态；
- 原文件路径和尺寸；
- 是否含用户姓名、头像、手机号、班级、订单、内部账号等敏感信息；
- 能观察到什么，以及无法从单张图判断什么。

### 4.2 分两遍检查

1. **全图检查：**识别设备/页面壳、主要区域、信息层级、主任务、主次操作、反馈位置和整体密度。
2. **局部检查：**以原始分辨率查看关键区域，核对文案、按钮状态、选中/禁用、弹层、错误提示、留白和裁切。

需要时先生成带编号的标注图，再根据编号建立观察表。可使用：

```bash
python3 scripts/annotate_reference_screenshot.py \
  --spec /absolute/path/to/screenshot-annotations.json \
  --out /absolute/path/to/annotated.svg \
  --png /absolute/path/to/annotated.png
```

### 4.3 区分观察与推断

每条记录必须标记：

- `observed`：截图中直接可见，例如“底部存在一个主按钮”；
- `inferred`：根据模式推测，例如“点击后可能进入确认弹层”；
- `unknown`：单张图无法判断，例如“失败后是否保留选择”。

`inferred` 和 `unknown` 不能成为目标交互的事实来源。正式 PRD 没有确认时，写为待确认或排除，不偷偷进入按钮、连线和结果页。

### 4.4 从截图提取什么

提取对评审有用的结构，不机械 OCR 全屏：

- 页面壳与导航；
- 区域顺序、分组和视觉优先级；
- 关键可见内容、控件类型和主次操作；
- 状态线索：选中、禁用、加载、弹层、错误、空态；
- 可复用组件和视觉惯例；
- 本次方案需要保留、替换、移动或删除的区域。

截图不提供隐藏状态、完整动作集合、返回/重进规则、权限或跨系统结果。若同时能读取设计节点、组件树或可访问性结构，把它们作为补充证据，但仍保持产品事实与视觉证据分离。

## 5. 页面与故事板设计

### 5.1 先规划评审问题

每个原型资产先写一句读者问题。常见输出不是固定套餐：

| 读者问题 | 合适表达 |
|---|---|
| 现状哪个区域需要变化 | 局部裁切 + 编号标注 |
| 页面有哪些稳定区域和主操作 | 页面地图或单状态低保真 |
| 条件改变后哪里不同 | 并列状态对比 |
| 用户一次任务如何连续完成 | 关键帧故事板 |
| 全部状态和迁移是否闭环 | 状态模型或可缩放全景，不用手机卡片堆砌 |
| 全部关键页面、页面状态和跳转是否能连续追踪 | 页面交互总览：页面卡片 + 带动作或条件的连线 |

### 5.2 设计单个页面

每个关键状态至少能回答：

- 用户此刻的任务是什么；
- 第一眼必须看到什么；
- 主要信息、辅助信息和风险提示如何分组；
- 主操作、次操作、禁止操作分别是什么；
- 操作反馈出现在哪里，是否靠近触发点；
- 与相邻状态相比，信息、操作或结果改变了什么。

低保真不是所有内容都画成灰框，更不是把未决问题画成虚线"占位"框。文字、真实状态文案和按钮标签若影响判断，应直接显示；与评审无关的装饰、占位数据和精细样式应省略。具体规则：

- 页面只呈现产品经理已决定的内容：真实文案（来自正式 PRD）、具体示例数据、已决定的按钮与状态；
- 业务规则必须翻译成用户可见的界面元素：限制条件画成横幅提示，防重复提交画成禁用态按钮，资格失效画成拦截页文案；禁止在页面内放置"防误触：xxx""规则：待定"式虚线注释框；
- 未决定的业务问题不进原型：写进正文缺口清单或返回上游；
- 结构示意保留"不代表最终布局"声明，但视觉必须干净到可以直接评审。

### 5.3 设计连续故事板

以一个用户任务为单位选择关键帧：进入/准备 → 用户动作 → 即时反馈或处理中 → 明确结果/恢复。关键帧数量由状态变化决定，不按固定数量裁剪。

- 在相邻帧之间标动作或系统事件，不用“下一步”；
- 主线沿统一阅读方向，分支靠近分歧点；
- 同一结果的多个原因可在展示层收敛，底层模型保留完整迁移；
- 并列状态只展示真正变化的区域，必要时高亮差异；
- 返回、取消、重进和失败恢复若会改变结果，必须在故事板或相邻规则中出现；
- 无连线的页面组只能称状态概览，不能称交互故事板。

### 5.4 设计页面交互总览

页面交互总览先画完整主操作顺序，再从每个判断或动作处分叉。页面卡片保留足以识别状态的标题、关键信息、主次操作和反馈，不追求高保真；系统校验和接口调用只有在改变页面去向时才作为连接条件或简化系统节点出现。

页面卡片必须使用可识别的缩略界面结构，而不是圆角矩形内放三行状态说明。至少呈现：当前任务、1—3 个关键信息区、主操作或明确的不可操作状态、当前反馈。卡片之间再用带语义连线表达动作和结果。若当前工具无法生成这种页面卡片，应改用“产品主流程 + 分页面局部故事板”，不得把状态网络命名为页面交互总览。

- 相同页面壳但主操作、反馈或恢复改变时拆为不同状态卡；
- 同一目标页面的多个原因可以收敛在一条连线上，用原因组或编号下钻；
- 返回、取消、重试和重进使用与前进路径有区别的线型；
- 页面外部出口使用轻量节点，不伪造其内部界面；
- 先保证从入口可以逐线复述所有结果，再优化对齐、留白和视觉层级；
- 总览过宽或过高时，保留一张可缩放全景，同时在正文放区域预览或分段导览，不能删分支换取美观。

## 6. 执行与渲染

复杂或会重复更新的原型先使用 `assets/prototype-plan-template.json` 建立计划，并运行：

```bash
python3 scripts/check_prototype_plan.py \
  --plan /absolute/path/to/prototype-plan.json
```

执行顺序：

```text
登记正式 PRD、设计资产和截图
→ 判断产品语义与视觉上下文充分度
→ 选择复用、标注、适配、低保真或只规划
→ 建立 Surface、区域、状态与输出计划
→ 先做一张代表性资产并查看
→ 按区域或任务增量生成
→ 装配进对应正文位置
→ 检查正文宽度、放大视图和交互连续性
```

工具选择服从资产目标：

- 已有设计系统或可编辑设计文件：优先复用组件、变量和现有页面；
- 现状截图或已确认视觉：优先标注、裁切和差异表达；
- 无设计资产但语义稳定：使用 `scripts/build_screen_html.py` 生成 HTML 低保真原型（组件词汇见 `scripts/mobile_screen_kit.py`），经 `scripts/capture_html_png.py` 无头浏览器截图出 PNG；无浏览器环境退回 `scripts/render_wireframe_board.py`；
- 复杂状态关系：使用状态图或可缩放画板；
- 飞书只负责发布与阅读，不应反向决定产品原型结构。

不要把 Figma、飞书画布、Mermaid、SVG 或某个节点数阈值写成所有需求的强制规则。

## 7. 验证与返工

自动检查负责发现证据角色混淆、输入不足却生成完整交互、截图断链、状态/迁移缺失和输出计划不完整。人工至少检查：

- 设计正确性：所有页面行为和状态能回到正式 PRD；
- 信息完整性：入口、关键信息、操作、反馈、结果和恢复按适用性覆盖；
- 视觉清晰度：主任务突出，状态差异明显，动作标签属于唯一迁移；
- 参考一致性：已确认设计被复用，现状截图没有被误当目标方案；
- 渲染质量：无裁切、错位、重叠、小字和敏感信息；
- 文档装配：视觉紧邻对应逻辑，文字不重复逐帧复述；
- 独立阅读：非作者能按图复述任务、分支和结果。
- 页面真实性：读者能从页面卡片或局部原型识别这是哪个页面、此刻要做什么、主要操作在哪里；只有状态标题和说明文字的不通过。
- 变化承接：源文档中与本期变化直接相关的截图/设计已被查看并复用、标注或明确说明不适用，没有静默丢失。

返工按根因处理：产品行为缺失回上游；证据角色错误回输入层；关键帧或信息层级错误回设计语义层；错位、裁切和交叉回渲染层；正文看不懂回装配层。

## 8. 方法来源

只吸收可迁移的方法，不复制工具约束或平台语法：

- [Figma MCP screen-building workflow](https://github.com/figma/mcp-server-guide/blob/main/skills/figma-generate-design/SKILL.md)：先检查现有页面和设计系统，按区块增量构建，再分别查看整体与局部截图。
- [Storybook](https://github.com/storybookjs/storybook) 与 [test runner](https://github.com/storybookjs/test-runner)：把界面状态作为可独立呈现、可执行验证的场景，而不是只检查一张最终页面。
- [XState](https://github.com/statelyai/xstate)：用显式状态、事件、迁移和图遍历保持复杂交互可预测、可检查。
- [Playwright visual comparisons](https://github.com/microsoft/playwright/blob/main/docs/src/test-snapshots-js.md)：保留稳定基线、在一致环境下比较渲染结果，并人工审阅变更。
- [Microsoft OmniParser](https://github.com/microsoft/OmniParser)：将截图拆成结构化可理解元素；本 skill 只借鉴“先结构化再行动”，不要求安装模型。
- [GitHub screenshot guidance](https://docs.github.com/en/contributing/writing-for-github-docs/creating-screenshots)：只在空间定位确有帮助时使用截图，保留恰当上下文并处理敏感信息。
- [Mermaid layout reference](https://github.com/mermaid-js/mermaid/blob/develop/docs/intro/syntax-reference.md)：根据关系复杂度选择布局，布局算法只解决排布，不替代语义拆分。
- [baoyu-design](https://github.com/JimLiu/baoyu-design)：原型/线框的默认载体是自包含 HTML + 浏览器截图预览；"不加填充内容、不用占位文字、真实数据、44px 触控目标、CJK 字体栈"等工艺标准已并入本 skill 的组件系统（`scripts/mobile_screen_kit.py`）。
- [ui-mockup-desktop-workbench](https://github.com/PANGKAIFENG/ai-product-manager-skills/tree/main/skills/ui-mockup-desktop-workbench)：先结构（页面清单、状态模型、ASCII 布局）后视觉的门禁式推进，与本 skill 的原型计划/检查器分工一致。
