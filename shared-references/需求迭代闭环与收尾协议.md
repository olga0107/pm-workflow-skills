# 需求迭代闭环与收尾协议

> 适用于在已有产品上调整业务规则、角色关系、统计指标、结算口径、状态流或跨模块行为的迭代。它不是另一套 PRD 模板，而是把“规则变更容易漏什么”和“发版前如何收口”变成跨 skill 的最小检查协议。

## 1. 什么时候启用

命中任一条件时启用；普通文案、纯样式、无行为变化的重构不必展开完整协议：

- 修改已有业务规则、等级 / 权益 / 指标 / 结算口径；
- 一个实体从单一归属变为多角色、多主体或多对多关系；
- 结果受时间、批处理、定时任务、事件结束或人工操作时序影响；
- 需要重算、补算、冻结、回滚、去重、历史兼容或数据迁移；
- 同时影响页面、云函数 / 接口、后台、任务、数据、运营规则或文档；
- 用户提出“验收后收尾审查”“提审发版前检查”“有没有遗漏 / 冗余”。

按风险裁剪：命中一个条件至少做变更台账和影响地图；命中时序、结算或历史数据时，再做冻结与重算规格；准备交付或发版时做闭环收尾。

## 2. 四张最小表

### 2.1 规则变更台账

| 规则项 | 旧规则 | 新规则 | 明确不变 | 生效范围 / 时间 | 历史数据处理 | 来源 / 状态 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  | confirmed / inferred / assumed / unknown |

禁止只写“支持”“优化”“纳入统计”。必须说明计算对象、计算时点、是否重复计入、对既有数据是否追溯。

### 2.2 影响地图

| 影响层 | 要检查的对象 | 本次是否受影响 | 验证 / 交付物 |
|---|---|---|---|
| 用户入口与页面 | 展示、提示、权限、状态、空态、历史记录 |  |  |
| 业务写入 | 关系、状态、快照、流水、幂等键 |  |  |
| 派生计算 | 实时刷新、批量结算、重算、补算、排名 / 等级 |  |  |
| 触发链路 | 创建、变更、结束、签到、评价、取消、定时任务 |  |  |
| 运营 / 后台 | 配置、审核、导出、人工补偿、排障入口 |  |  |
| 测试与观测 | 场景数据、日志、失败记录、积压量、告警 |  |  |
| 文档与发布 | 稳定知识、需求包、验收清单、更新说明、部署清单 |  |  |

“未受影响”也要给出理由，不能因没有改代码就默认不受影响。

### 2.3 时序与归属表

凡是结果可能因后续变更而改变，至少回答：

| 问题 | 必须明确的内容 |
|---|---|
| 事实何时发生 | 关系建立 / 修改、活动结束、结果产生、批处理执行的时间点 |
| 何时冻结 | 以哪个业务事件生成不可随意变化的快照或归属 |
| 冻结前变更 | 影响当前关系、临时预览，还是正式指标 |
| 冻结后变更 | 是否禁止；若允许，是否只重算结果不重选归属 |
| 结果变化 | 哪些事件触发重算，是否补发 / 扣回，如何处理迟到数据 |
| 重复与幂等 | 同一主体多角色、任务重试、重复触发、并发执行如何去重 |
| 中断与恢复 | 批处理失败后如何记录积压、续跑和人工排障 |
| 历史边界 | 新规则从何时 / 哪些数据开始，是否回溯，如何兼容旧记录 |

推荐将“关系变更”与“结果变更”分开：前者通常更新归属或快照，后者才重算已确认归属主体的派生指标。只有业务明确要求实时临时值时，才增加未冻结指标，并明确其不参与正式结算 / 等级 / 权益。

| 闭环项 | 完成条件 | 状态 |
|---|---|---|
| 需求与 PRD | 新旧规则、非目标、时序、异常和验收口径一致 |  |
| 实现 | 影响地图中的代码、任务、数据和页面均已核对 |  |
| 验收 | 主流程、边界、异常、旧数据和幂等场景有结果证据 |  |
| 质量与观测 | 静态检查、运行验证、失败记录和积压可观测 |  |
| 稳定知识 | 验收通过后已同步长期有效规则和工程事实 |  |
| 需求包 | 实际修改、验收清单、残余风险和资料入口已更新 |  |
| 状态 | 交付状态与发布状态分开，未将待发布写成已上线 |  |
| 同步说明 | 更新说明只引用已确认事实，并列出发布前后动作 |  |

## 3. 规则变更的默认判定原则

- **先定业务冻结点，再定技术实现**：不要先按方便的批处理时点实现，再反推业务归属。
- **当前关系不等于历史事实**：需要稳定结算的关系，应记录可追溯的冻结归属 / 快照；不能仅依赖结算当天的当前字段。
- **正式值与预览值分离**：活动未结束、审批未完成或条件未满足时，不把临时结果写入正式累计、等级、权益或结算；若保留预览，必须单独标记。
- **归属计算与指标计算分层**：先确定“谁获得这次贡献”，再计算“贡献是否有效、好评、奖励或等级变化”。
- **多角色去重且保留审计**：同一主体在同一事件中承担多个角色时，业务贡献通常只计一次，但角色身份仍应保留用于追溯。
- **重复执行必须安全**：批任务重跑、网络重试、并发触发不得重复增加累计值、奖励或流水。
- **历史边界必须显式**：新规则默认只作用于生效后的新事件；若要回溯，必须单独写范围、迁移 / 补算、校验和回滚，不以“顺便兼容”带过。
- **发布状态不能反推业务事实**：验收通过可同步长期规则，但只有明确生产发布确认后才写“已发布”。

## 4. 何时可以收尾

收尾审查不是再做一次泛泛代码 review，而是回答四个问题：

1. **规则有没有漏**：旧规则、新规则、明确不变项、历史边界、非目标和所有触发时点是否一致？
2. **链路有没有漏**：入口、写入、派生计算、异步任务、页面展示、后台、测试数据和观测是否都在影响地图中有结论？
3. **失败能不能处理**：幂等、重试、中断、积压、补偿、回滚和排障信息是否足够？
4. **交付是否闭环**：代码、验收、稳定文档、需求包、状态和更新说明是否对齐？

只有“无未解决 Blocker / Major，或 Major 有责任人和完成条件”时，才可报告 `PASS` 或 `PASS_WITH_CONDITIONS`。报告“可提审”时必须另列发布前部署顺序、发布后抽查和未完成事项。
