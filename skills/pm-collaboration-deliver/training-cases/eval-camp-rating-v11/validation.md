## 2. 基线失败与返工

### 2.1 局部原型单列过高

新版评价填写最初按三个页面状态纵向堆叠，渲染高度达到 1964px，触发 renderer 的高度门槛。返工后按阅读逻辑改成“未完成在上，低分与可提交并列在下”，既保留分支关系，也更适合飞书正文宽度。

结论：不应给页面数量或节点数量设固定值，但必须让布局由读者任务、分支结构和目标平台共同决定；高度门槛应继续保留为返工信号。

### 2.2 飞书 preview 扩展名误判

第一次把画板 preview 输出名预设为 `.png`，飞书实际返回 JPEG，5 次导出均被 CLI 拒绝。改用 `.jpg` 后全部成功。

结论：飞书发布指南新增“省略扩展名或先确认响应格式；严格审计以 board token 命名”的规则，避免其他需求重复踩坑。

### 2.3 资源 preview 与正文阅读态混淆

飞书资源 preview 使用近方形画布，宽图下方出现较大留白。这个现象只能说明预览容器的宽高策略，不能直接证明正文画板也有同样留白。浏览器阅读态未成功加载，因此本轮只判定“画板资源渲染通过、正文阅读态待验”。

结论：skill 已明确拆分两个证据面。以后严格发布不得用画板 preview 代替正文阅读视图。

### 2.4 多状态聚合可能隐藏业务差异

全局总览将“首次/替代 × 正常/低分”四种结果聚合进同一结果卡。图中确实画出了四个变体，但原 overview spec 只保存四个状态 ID，没有强制保存每个变体的可见差异，未来生成器可能只保留一个笼统结果框。

结论：新增 `state_variants` 校验。一个卡片聚合多个状态时，必须逐状态写出标签和差异；只有视觉与读者结论确实等价时，才可使用 `visual_equivalent=true` 并说明原因。

## 3. 产物质量评估

### 做得较好

- 传统 PRD 主干保持为背景、目标、范围、产品方案、需求详情、通用规则、上线影响和验收，没有把内部执行日志塞进正文。
- 主流程、全局页面连线和局部原型分工明确：主流程建立心智，全景保证分支完整，局部原型承接页面细节。
- 原型承接了现有 APP 与后台截图的页面壳，但业务行为只以正式 PRD 为准，没有从截图猜测积分、锁定或失败规则。
- 前后台没有被混成一条巨大链路；全景分为学员评价与后台查询导出两条阅读泳道。
- 首次、替代、低分、锁定、失败和重试均有页面级表达，不依赖读者从长表格自行拼逻辑。

### 仍有不足

- 总览画板信息量大，必须依赖缩放；它不能替代正文中的主流程和三张局部图。
- 局部故事板为保证卡片整齐使用统一高度，部分状态下半区存在留白。当前不影响理解，暂不为此增加自适应高度复杂度；后续再用更多真实案例判断是否值得抽象。
- 飞书正文实际缩放、表格布局和图文邻接仍需一次可用浏览器或人工阅读态复核，本轮不宣称通过。
