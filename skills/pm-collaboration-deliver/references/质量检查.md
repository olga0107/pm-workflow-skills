## 1. 语义检查

### 需求背景

- 是否写清角色、场景、目的、当前行为和现状数据；
- 是否只包含客观事实、证据、约束和已发生事件；
- 是否混入“体验差、能力不足”等问题判断或本期方案；
- 数据是否有口径、来源和时间，没有数据时是否说明缺失原因。

- 是否指出现状中具体哪个环节与预期不符；
- 是否能从背景事实推导，而不是新增无证据判断；
- 是否说明需求未满足、流程阻断或体验问题影响谁、范围和程度如何。

### 需求目标

- 是否写清本需求希望改变的用户或业务状态；
- 目标是否从背景和问题推导，并能通过产品结果验证；
- 是否误写成新增页面、支持功能、开发上线或实施步骤；
- 没有可信基线时是否避免制造数值目标。

### 需求范围

- 是否明确本期做什么、不做什么；
- 是否写清必要的端、角色、场景和版本边界；
- 是否混入研发任务或未确认的后续方案。

### 方案与需求详情

- 产品方案是否用最短路径说明入口、关键动作与结果；
- 每个主要页面或任务是否写清入口、信息、操作、结果及必要状态/恢复；
- 页面内规则是否就近，跨功能规则是否确实影响两个以上模块；
- 是否混入 API 字段、队列、存储、算法等研发 spec。
- 详情标题是否直接说明“什么对象发生什么变化”；
- 界面需求是否把原型、信息项和对应逻辑就近编排，而不是让读者跨页找规则；
- 直接替换是否写清前后变化，条件交互是否补默认值/校验/反馈/生效，跨端状态是否补端差异/优先级/持久化/恢复。
- 界面变化是否实际承接了输入中的截图/设计，或在语义完整但无视觉上下文时为核心变化页生成了低保真；是否出现“源文档有图、成稿却纯文字”的断层。

### 效果验证（若保留）

- 指标、计算方式、数据来源和验证用途是否清楚；
- 是否只保留真正需要上线后判断的结果、行为或护栏；
- 是否把研发验收用例误放在效果验证中。

## 2. 章节取舍检查

- 需求目标是否描述可验证的用户或业务状态，而非功能产出或交付过程；
- 方案流程是否存在多角色/系统/时间交接，而不是简单步骤装饰；
- 场景拆分是否确有多用户、多场景或多套方案；
- 版本拆分是否每期都有独立价值，而不是开发排期；
- 产品动线是否存在入口、跳转、返回、取消、失败或重试变化；
- 信息结构图或原型是否承担页面空间和信息层级问题；
- 效果验证是否会用于上线后的继续、调整、补实验或止损判断；
- 所有不适用章节是否已直接删除，没有空标题或大段“不适用”。

## 3. 同源检查

从正式 PRD 正向抽查：

1. 现状事实、主要问题、目标和范围均有正文归宿；
2. 每个 P0 功能在传统 PRD 中有正文归宿或明确下钻；
3. RULE、状态矩阵和数据口径中的高影响条件已回到相关页面/任务；
4. AC 暴露的关键异常、权限、兼容和恢复没有被压缩掉。

从传统 PRD 反向抽查至少 5 条高影响结论，优先选择权限、禁止结果、时间、数值、状态和数据口径；每条都应能在正式 PRD定位。无法定位的结论删除或返回上游确认。

## 4. 信息分层检查

- 主文档是否仍是传统 PRD，而不是协作简报、执行报告、生成说明或研发清单；
- 第一屏是否先建立背景、问题和目标，再进入方案；
- 用户主线能否在不理解内部系统名、错误码或实现方式的情况下读懂；
- 必要的系统职责是否集中在产品方案的流程或职责表，而非散落全文；
- 接口字段、鉴权、幂等实现、并发方案、队列、存储、算法和日志结构是否已进入研发 spec；
- 是否用产品结果约束替代实现手段，例如“重复进入不能产生第二次有效结果”；
- 内部模型、执行包、来源 IDs、检查记录和生成术语是否完全退出正文。
- URL、query 参数、HTTP 状态码、Node、缓存键等实现表达是否已转换为用户入口、页面状态、操作和结果；确需保留的精确值是否集中到下钻而非散落正文。

## 5. 人类阅读检查

作者先用下列问题检查成稿；严格验证时，再让没有本轮对话上下文的人只读传统 PRD并回答：

1. 当前谁在什么场景下做什么，客观事实和数据是什么；
2. 现状中哪个环节存在什么问题，影响谁；
3. 本需求希望改变什么用户或业务状态；
4. 本期做什么、不做什么，选择了什么总体方案；
5. 用户怎样完成主要任务，关键页面和结果是什么；
6. 哪些状态、权限、异常或时间会改变结果；
7. 若存在数据与效果验证，使用什么口径判断目标是否达到；
8. 完整验收或实现细节去哪里查。

基础验证记录作者发现的缺失、歧义和下钻断点；严格验证再记录独立读者的答对、误解和隐含前提。前六问需要作者口头补充主要产品事实时，文档不通过。第七问只在相关章节适用时回答；第八问可以下钻正式 PRD。

## 6. 编排与视觉检查

- 第一屏是否依次建立背景、问题和目标，而不是先摆方案或生成说明；
- 章节是否按需求结构裁剪，是否存在模板填空感；
- 同一事实是否在概览、规则和详情中反复扩写；
- 一个段落是否同时承担背景、问题、方案、异常和实现；
- 表格是否过宽且需要频繁横向扫描；
- Mermaid 是否先建模角色/状态/动作/结果，节点是否过多、分支是否有标签、失败是否有落点；
- 页面图是否标明现状、目标、结构示意或参考；
- 图片是否可打开、未裁切、文字可读且无敏感信息。
- 是否为简单需求强行增加流程图或信息结构图；验收标准可以很短，但不能缺失；
- 是否用“同原逻辑/保持一致”掩盖本次差异，而没有列清例外和变化。
- 每个视觉是否对应独立读者问题，并按顺序、交接、状态、空间、条件或层级关系选择了合适表达；
- 是否只在不同抽象层无法由一张图清楚承担时分层，且没有重复画同一逻辑；
- 详情是否按内聚的用户任务聚合，同一高风险事实是否只有一个主要正文归宿；
- 是否把完整状态模型直接渲染成正文巨图，或让一张图同时承担系统交接、用户动线、页面空间和完整状态覆盖；
- 总览图是否只建立全局心智，局部原型是否紧邻对应任务，完整全景是否在需要时作为可缩放下钻；
- 交互版是否区分 `coverage=focused` 的展示子图与 `coverage=complete` 的核查视图；
- 原型是否覆盖确认、处理中、成功/失败等真正改变用户操作和反馈的关键状态，而非只展示静态页面壳；
- 是否分别判断了产品语义和视觉上下文充分度，没有因“有截图”就补造隐藏交互；
- 已确认设计是否优先复用；现状截图和参考图是否明确标注角色；观察、推断和未知是否分开；
- 单页原型是否有清楚的主任务、信息层级、主次操作和就近反馈；故事板关键帧是否由状态变化决定并标明动作；
- 在正文实际宽度下，标题、节点、动作和状态差异是否无需放大即可读清；
- 在独立画板放大后，主线、回边、分支标签和异常归属是否仍可追踪；
- 页面交互总览中的页面卡片是否具有可识别的缩略界面结构；若只是圆角框加状态说明，必须降级命名为状态网络或改做真正页面卡片。
- 轻量需求是否被元数据、固定章节和重复表格扩写；若成稿明显长于输入，新增篇幅是否都在解决真实理解问题。

## 7. 自动检查

基础路径可运行：

```bash
python3 scripts/check_reading_view.py \
  --profile traditional-prd \
  --document /absolute/path/to/traditional-prd.md \
  --source /absolute/path/to/formal-prd.md
```

脚本只发现结构、密度、断链和模板残留，不能替代语义、同源和真实阅读检查。普通单点文档不因没有执行包而失败。

增强路径先运行执行包检查，再使用 `--fail-on-warnings` 运行阅读视图检查：

```bash
python3 scripts/check_execution_pack.py \
  --pack /absolute/path/to/execution-pack.json

python3 scripts/check_reading_view.py \
  --profile traditional-prd \
  --fail-on-warnings \
  --document /absolute/path/to/traditional-prd.md \
  --source /absolute/path/to/formal-prd.md
```

复杂交互还要让执行包声明 `interaction_model`，并可单独生成覆盖报告：

```bash
python3 scripts/check_interaction_model.py \
  --model /absolute/path/to/interaction-model.json \
  --report /absolute/path/to/interaction-coverage.md
```

执行包检查会联动检查交互模型。交互检查覆盖载体/页面、状态、可用操作、迁移、异步成功失败、可达性与视觉引用；它不能证明业务语义正确，仍需依据正式 PRD 完成人工正向与反向抽查。

复杂原型、截图承接或设计资产复用还应运行：

```bash
python3 scripts/check_prototype_plan.py \
  --plan /absolute/path/to/prototype-plan.json
```

该检查阻止输入不足时生成完整交互、截图单独授权产品行为、已确认设计被无理由重画，以及输出与证据、Surface、状态或迁移断链；它不能替代实际查看原图、局部裁切、最终原型和发布后的正文。

飞书的日常发布只需回读正文并查看已发布视觉；严格飞书交付再读取[飞书发布与渲染](./飞书发布与渲染.md)的审计部分并运行：

```bash
python3 scripts/check_feishu_delivery.py \
  --audit /absolute/path/to/feishu-delivery-audit.json
```

自动检查只能提示骨架缺失、内部术语、重复、密度和断链。图形是否选对、内容是否聚合、视觉是否在最终平台真正清楚，仍需要查看成品和读者测试。

## 8. 通过标准

- 主链完整：需求背景 → 需求目标 → 需求范围 → 产品方案 → 需求详情 → 验收标准；
- 需求目标不是功能产出或交付过程；数据与效果验证只在适用时出现；
- 主要产品行为与正式 PRD 同源；
- 非作者可以连续理解并开始第一次协作；
- 图、表、原型和文字各自承担不同问题；
- 文档没有内部工作过程、追溯外壳、空模板或 AI 总结腔。
- 执行路径的页面状态没有不可达或无出口，高风险规则在正文和视觉中均有一致归宿；最终资产已经实际查看，不以脚本退出码代替视觉验收。
- 严格验证时，无上下文读者测试已覆盖预设问题、歧义、隐含假设和矛盾；发现的问题已回到对应阶段修正。
