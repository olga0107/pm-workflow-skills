## 1. 表达计划

每个表达项先记录：

- 读者需要回答的具体问题；
- 正式 PRD 来源；
- 核心关系：顺序、交接、状态、空间、条件、层级或对比；
- 选择的表达及选择理由；
- 明确包含与排除的内容；
- 正文放置位置；
- 视觉角色：总览、局部或下钻；
- 正文内联还是独立可缩放；
- 语义和渲染如何验证。

先判断短文或小表能否直接回答。只有视觉明显降低理解成本时才画图；不能把章节标题直接转换成节点。

## 2. 路由规则

| 核心关系 | 首选表达 | 需要换型的信号 |
|---|---|---|
| 连续步骤与条件分支 | 流程图 | 重点其实是参与方随时间交互时改用泳道/时序 |
| 多角色或多系统交接 | 泳道或时序表达 | 只需要责任边界、不涉及顺序时用职责表 |
| 单一对象状态与事件迁移 | 状态图 | 混入多个对象或大量页面空间时拆开 |
| 页面区域、控件和反馈位置 | 原型或状态对比 | 只说明字段口径时改用表格 |
| 条件组合到确定结果 | 决策表 | 条件本身形成用户路径时使用流程图 |
| 信息父子层级 | 信息结构图 | 只是章节目录时不画 |
| 范围、职责、字段和简单事实 | 短文、小表或列表 | 不使用装饰性视觉 |

同一需求可以组合多种表达，但每种必须回答不同的读者问题。

## 3. 四层视觉架构

### 3.1 总览层

用于建立共同心智，只回答一个跨模块问题。跨系统协作用泳道/时序，用户任务用产品动线。总览不承担完整页面空间、字段规则或全部状态覆盖。

### 3.2 页面交互总览层

用于把页面卡片、页面内关键状态、主次操作和跳转条件放在同一张可追踪画布上。主操作沿一个稳定方向排列；加载、空态、失败、成功、取消、返回和重进从对应分歧点展开。它承接产品动线，但比纯流程图更具体；它统领局部故事板，但不替代字段规则和页面细节。

页面交互总览默认用于多页面、多分支交互版。页面卡片必须来自交互模型和原型证据；连线必须映射模型迁移。不能把没有页面内容的流程节点改名为页面交互总览，也不能把无连线页面画廊当作总览。

### 3.3 局部任务层

与需求详情相邻，用连续关键帧、状态对比或局部原型解释一个用户任务。每张局部图同时让读者看见关键内容、主操作和操作反馈；异常放在发生位置附近，原因很多但结果相同时使用原因组或决策表收敛。

### 3.4 完整核查层

完整状态模型、覆盖报告和全景图服务于查漏。它们不自动进入正文。只有满足以下条件之一时才交付全景：

- 评审任务本身需要检查全部状态和迁移；
- 设计、研发或测试需要一个可缩放的共同索引；
- 用户明确要求完整交互画板。

全景在正文宽度下不可读时，提供独立画板/链接，正文只放产品主流程、页面交互总览的可读预览和局部子图。不得把“底层迁移完整”解释成“所有迁移必须画在同一张正文图”。

## 4. 流程与关系图工作流

### 4.1 建立语义骨架

从正式 PRD 提取本图所需的最少事实：入口、参与方、动作、判断、交付物、状态变化、结果与恢复。先写无样式的节点和边清单，再选择方向、分组和图形语法。

节点写可观察的动作、页面反馈或业务结果；判断写成问题；互斥分支写清条件；跨角色连线说明交付物或状态变化。不要在节点中塞完整规则、字段或验收句子。

### 4.2 根据阅读方向布局

- 连续任务优先沿自然阅读方向展开；
- 层级或多分支判断选择能减少宽度和交叉的方向；
- 角色或系统存在稳定边界时分组；
- 返回和重进保留真实语义，不为排版删除；
- 状态图只描述一个主要对象，状态用名词，迁移用事件或条件。

数量不是拆图门槛。出现下列实际问题时才调整：

- 一张图混合多个抽象层或多个独立读者问题；
- 关键路径被次要异常、回边或交叉线遮蔽；
- 标签、节点或分组在目标平台缩放后不可读；
- 不同受众只需要其中一部分；
- 同一图同时试图表达顺序、生命周期和页面空间。

优先尝试重新分组、改变方向或压缩原因；仍不清楚时按评审问题、语义层或受众拆图。不要为了减少节点删除正式 PRD 中的分支。

流程图默认使用 `scripts/render_flow_diagram.py`（模板 `assets/flow-diagram-template.json`，语义检查 `scripts/check_flow_diagram.py`）：分层布局、判断菱形、正交圆角连线、返回虚线均在本地完成，不依赖 mermaid-cli、graphviz 或网络。`.mmd` 只在团队已有 mermaid 工具链时作为可选交换格式导出。精确页面空间和局部故事板使用 `scripts/build_screen_html.py` 的 HTML 组件系统。工具只负责布局和渲染，不能替代语义拆分。

### 4.3 语义检查

- 每个非入口节点有来源，每个非终点节点有去向；
- 每个判断的分支含义明确，互斥或覆盖关系能解释；
- 终点是用户或业务结果，而不是“完成处理”；
- 失败、取消、返回、重进和人工兜底回到正确位置；
- 图中没有主源未定义的页面、状态、按钮或结果。

## 5. 原型工作流

### 5.1 选择资产层级

先完整读取[原型设计与截图承接](./原型设计与截图承接.md)，分别判断产品语义充分度和视觉上下文。优先复用已确认设计；现状截图先作为观察证据，不能自动成为目标方案。只有评审需要页面空间、信息优先级、操作和反馈位置，语义达到可生成深度，且没有可用正式资产时才生成低保真结构示意。局部变化优先局部标注，不重画整页。

### 5.2 从交互模型生成

先读取[交互型 PRD 与状态模型](./交互型PRD与状态模型.md)，再确定本张原型回答哪个任务：

- 用户进入时看到什么；
- 当前哪些操作可用；
- 操作后页面如何反馈；
- 成功、失败、空态、已完成或资格失效如何区分；
- 返回、取消和再次进入去哪里。

复杂原型先使用 `assets/prototype-plan-template.json` 建立证据、Surface、区域、复用策略和输出计划，并运行 `scripts/check_prototype_plan.py`。截图输入先检查原图与关键裁切，区分观察、推断和未知；需要编号标注时使用 `scripts/annotate_reference_screenshot.py`。需要低保真线框时使用 `scripts/build_screen_html.py`（模板 `assets/mobile-screen-storyboard-template.json`，组件词汇见 `scripts/mobile_screen_kit.py` 头注）并用 `scripts/capture_html_png.py` 截图出 PNG；只有无可用浏览器环境时才退回 `scripts/render_wireframe_board.py` 灰盒渲染器。复用页面壳和组件配方，只替换当前需求的内容、状态和布局。

需要页面交互总览时，先从交互模型选定卡片粒度：稳定页面壳相同但主信息、主操作、反馈或恢复不同的状态要拆卡；纯系统判断可作为连接器或系统节点；既有外部页面只画简化出口；`visibility=transient` 的加载/校验/处理中状态用 `chip` 扁条节点，不占页面卡、不画手机屏（加载态不是页面）。页面卡片的屏幕内容通过 `screen_source` + `screen_ref` 直接引用线框故事板 spec 中的屏幕定义，与需求详情章节的局部故事板保持同源，不在总览 spec 中重复描述屏幕内容。再使用 `assets/page-interaction-overview-template.json` 映射卡片与连线，并运行 `scripts/check_page_interaction_overview.py`。布局从主路径开始，随后在分歧点附近挂载异常和回边，不按固定页面数量或网格模板排版。

线框规格声明 `delivery_role`：正文资产使用 `inline` 并设置目标阅读宽度；完整全景使用 `zoomable`。渲染器按最终宽度推算字号和高度，不能通过时应拆成聚焦故事板，而不是提高固定节点上限。

正文内联的故事板默认只包含完成当前任务所需的连续状态。若需要完整交互核查，先从模型抽取展示子图；不要用手机页面卡片承载庞大的状态网络。完整生命周期更适合状态图，复杂全景更适合作为独立可缩放画板。

### 5.3 原型边界

- 结构示意必须标注“不代表最终布局”；
- 原型只承担空间、信息层级、状态、动作和反馈位置；
- 权限、业务条件、数据口径、异常与验收仍由正文或决策表承载；
- 没有确认的页面结构不生成看似确定的高保真设计；
- 单张截图不能证明隐藏状态、动作结果、返回、重进、权限或跨系统行为；
- 连续交互故事板必须标出动作和结果；无连线页面组只能叫页面/状态概览。
- 声明为完整交互画板的资产必须从同一状态模型生成，并明确 `coverage=complete`；局部故事板使用 `coverage=focused`，只核对声明的状态和迁移子集。
- 不在正文中并排展示过多完整手机页；优先截取关键区域或拆成相邻的任务故事板。

## 6. 文档装配

先判断是否存在不同抽象层的独立问题。例如：跨系统端到端任务链、用户产品动线、完整页面状态核查、单个任务的页面空间分别属于不同问题。若一张图能清楚回答全部问题，可以合并；只要混合后需要读者反复解码，就拆开。

装配时遵循：

1. 产品主流程放在读者需要建立任务心智的位置；多页面交互的页面交互总览紧随其后；
2. 局部视觉紧邻对应用户任务和规则；
3. 图前一句说明阅读目的；
4. 图后只补无法视觉化的限制与边界；
5. 图已承担顺序、状态或空间关系时，删除同构段落和大表；
6. 同一事实跨模块需要再次出现时使用引用或下钻。

## 7. 渲染检查与返工

第一版资产只代表结构已经生成，不代表可交付。必须实际查看目标平台中的图：

- 中文、字号、裁切和留白是否可读；
- 连线是否穿过文字、方向是否误导、条件标签是否贴近对应分支；
- 页面状态差异、按钮可用性和反馈位置是否清楚；
- 主线能否快速扫描，异常是否靠近发生位置；
- 图注和来源是否正确，是否含敏感信息；
- 图与上下文是否连续，是否需要读者来回翻找。

额外执行两种视图检查：

1. **正文宽度：**不放大时能否读清标题、节点、动作和状态差异；不能则拆分或改为局部图。
2. **放大视图：**独立画板中的完整路径、回边和异常是否仍可追踪；不能则改用状态图、按任务分区或减少可见迁移。

线条没有穿字不等于布局合格。还要检查主路径是否连续、长回边是否遮挡其他任务、标签是否属于唯一连线、视觉是否因过高或过宽而在正文中失去意义。

发现问题时按根因返工：语义错误回到事实或交互模型；图型错误重新路由；布局错误调整方向、分组或拆分；文字重复回到装配压缩。删除不能降低理解成本的视觉。
