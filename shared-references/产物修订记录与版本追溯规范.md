# 产物修订记录与版本追溯规范

> 适用于本工作流生成、维护或交接的需求定义、研究综合、竞品分析、指标复盘、需求分级、PRD、HTML PRD、质量审计、更新说明、上线观察和其他正式协作产物。目标不是记录每次文字改动，而是让协作者能回答：这份产物现在是哪一版、为什么变、谁确认、哪些旧结论已失效、下游是否需要重做。

## 1. 修订记录与决策台账的区别

两者都要保留，但不要混为一张表：

| 记录 | 回答的问题 | 适用范围 |
|---|---|---|
| **产物修订记录** | 这份文档从上一版改了什么、为什么改、影响哪些章节 / 下游 | 每一份持续协作的正式产物 |
| **迭代版本与决策台账** | 本次需求的业务原则、范围、技术或验收结论发生了什么变化 | 复杂迭代、跨文档或方案大改 |
| **质量审计记录** | 某个版本在什么阶段、基于哪些证据、是否达到交接门槛 | 需求定义、分级、PRD、HTML、发布收尾等需要审计的产物 |

修订记录可以引用决策 ID、审计 ID 或上游版本，但不复制完整讨论；决策台账也不能替代每份下游文档的修订记录。

## 2. 什么变化必须记录

以下变化必须新增一条修订记录：

- 新增、删除或调整目标、范围、非目标、角色、权限、状态、规则、指标、历史边界或发布条件；
- 改变方向、方案取舍、数据事实源、技术依赖、验收标准、风险等级或下游路由；
- 用户 / 评审方确认或否决一个会影响后续工作的决策；
- 修复事实错误、补充证据、改正过度确定的表述或更正验证状态；
- 用户验收后产生 UI / 文案 / 交互调整；
- 产物状态从草稿、讨论中、待验收、已验收、待发布、已发布、已归档等发生变化；
- 上游版本变化导致当前文档重写、局部失效、回退或重新审计。

以下变化可不单独记录：纯错别字、标点、格式、链接路径或不改变语义的排版修复；但如果这类修改影响阅读、追溯、状态或执行，仍应记录。

## 3. 统一记录格式

每份正式产物至少包含以下元数据和修订表：

```markdown
## 文档信息

| 字段 | 内容 |
|---|---|
| 当前版本 | v0.1 |
| 文档状态 | 草稿 / 讨论中 / 待评审 / 已确认 / 待验收 / 已验收 / 待发布 / 已发布 / 已归档 |
| 当前修订日期 | YYYY-MM-DD |
| 当前修订人 |  |
| 上游决策版本 | 例如：需求定义 v1.2 / 无 |
| 关联审计 | 例如：quality-audit v0.3 / 未审计 |

## 修订记录

| 版本 | 日期 | 阶段 / 触发 | 主要变化 | 影响范围 / 失效内容 | 确认人 / 责任人 | 状态 |
|---|---|---|---|---|---|---|
| v0.1 | YYYY-MM-DD | 初稿 | 建立初始事实与范围 | 初稿，无下游 |  | active |
```

字段要求：

- `版本`：推荐 `v0.x` 表示讨论稿，`v1.x` 表示已形成第一版正式结论；重大方案切换可递增主版本，如 `v2.0`；
- `阶段 / 触发`：写“用户确认”“评审反馈”“技术预验证”“测试发现”“UI 验收”“发布状态补录”等可理解原因；
- `主要变化`：写结果，不写“优化”“调整”等空泛词；
- `影响范围 / 失效内容`：明确章节、接口 / 页面 / 验收、下游文档或旧版本证据是否需要重做；无影响时写“无”；
- `确认人 / 责任人`：记录做出决定或负责补证据的人；未知时写“待补充”，不能伪造；
- `状态`：使用 `active`、`superseded`、`stale`、`pending-confirmation`、`archived` 之一。

## 4. 何时写入

### 4.1 创建产物

第一次形成可留档内容时写入 `v0.1`，不要等到“最终稿”才补历史。若只是临时对话草稿且不交给下游，可以不建立文件；一旦产物被引用、评审、交接或写入项目目录，就要有修订记录。

### 4.2 协作修改

每次完成一轮有明确结果的协作修改后立即追加记录，不要只在一天结束时凭记忆汇总。可以一轮包含多个小改动，但必须能让读者看出：

1. 触发了什么反馈或新证据；
2. 产物具体改了什么；
3. 哪些旧结论、旧证据或下游内容因此失效；
4. 下一步是否需要重新分级、重写、验证或审计。

### 4.3 重大变更

命中[需求迭代反复与方案大改治理指南](./需求迭代反复与大改治理指南.md)的变更时：

- 当前产物新增一条主版本修订；
- 旧版本记录保留并标记 `superseded`，不删除历史；
- 受影响的下游产物分别新增修订记录；
- 受影响的审计、截图、测试结果和发布判断标记 `stale`，直到重新审查；
- 不能只在文档末尾追加补充段落来掩盖版本切换。

## 5. 版本与状态规则

- “当前版本”只指该文件当前 active 的内容，不代表历史所有结论仍有效；
- “已确认”表示产品 / 评审方确认了该版本内容，不代表已经实现、验收或发布；
- “已验收”表示用户 / 测试确认，不代表生产已发布；
- “已发布”必须有生产版本、日期或明确发布证据；
- 上游版本变化时，下游不能静默继续使用旧版本；若影响未确认，状态至少为 `stale` 或 `pending-confirmation`；
- 修订记录不承担逐字记录聊天的职责。需要保留完整讨论时，链接到聊天、会议纪要、决策记录或证据材料。

## 6. 不同产物的最小记录重点

| 产物 | 最少要记录的变化 |
|---|---|
| 需求定义 | 问题、目标、方向、范围、非目标、决策状态变化 |
| 研究 / 竞品 / 指标 | 材料、样本、口径、证据强度、结论和建议变化 |
| 需求分级 | 等级、红线、交付门禁、体验复杂度和重分级依据 |
| PRD | 规则、页面、状态、权限、验收、范围和上游版本变化 |
| HTML PRD | 编译源版本、页面 / 状态 / 原型覆盖、审阅反馈和重新渲染状态 |
| 质量审计 | 审计对象版本、结论、缺陷、修复条件和复审状态 |
| 更新说明 / 上线观察 | 发布事实、角色影响、版本日期、观察结果和状态变化 |

## 7. 交接前检查

交给下游或报告“当前版本可用”前，检查：

- 当前版本、状态、修订日期和责任人是否可见；
- 修订表是否能解释最近一次重要变化；
- 上游版本和关联审计是否指向 active 版本；
- 旧版本、旧证据和受影响下游是否已标记失效；
- 文档内容、修订记录、状态和实际验证结果是否一致；
- HTML、截图、测试记录或更新说明是否来自同一版本。

如果无法确认当前版本或发现修订记录与正文冲突，不得报告 `ready`、`PASS`、`已验收` 或 `已发布`，应先做版本对账。
