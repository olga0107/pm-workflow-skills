## 1. 唯一主交付面

一次交付先选择一个主阅读面。默认是传统 PRD；用户要求飞书时，飞书文档就是主阅读面，本地 Markdown、XML、图片和画板源文件只作为构建材料。

以下是不同交付物，不得混成同一目录：

| 交付物 | 主要任务 | 默认状态 |
|---|---|---|
| 传统 PRD | 支撑产品、设计、研发、测试完成第一次共同评审并继续执行 | 唯一主文档 |
| 会议讲解稿/评审简版 | 帮助主持人在有限时间内讲清取舍和待决策 | 仅用户明确要求时附加 |
| 正式 PRD | 保存完整产品事实、验收、发布与 spec 交接 | 上游事实源和下钻 |
| 交互模型/执行包 | 检查状态、迁移、来源和跨资产一致性 | 内部证据 |
| 研发 spec | 说明字段、接口、存储、队列、算法和实现 | 下游文档 |

不要因为正式 PRD 很长，就把传统 PRD 改写成“一句话方案—评审重点—研发下钻”的简报。简报可作为附加视图，不能替代默认产品文档。

## 2. 传统 PRD 读者主线

传统 PRD 的稳定语义是：

```text
需求背景：现状是什么、问题在哪里
→ 需求目标：希望改变什么用户或业务状态
→ 需求范围：本期做什么、不做什么
→ 产品方案：如何从入口连接到结果
→ 需求详情：页面、功能、规则和状态如何工作
→ 验收标准：怎样判断产品结果成立
```

章节可以按需求复杂度合并小节或增加业务标题，但不能失去这条推理链。第一屏优先帮助读者理解背景、问题和目标；产品方案建立共同心智，需求详情支撑执行。修订记录、通用规则、影响与上线、数据与效果验证及关联资料按需出现。

不把下列内容设为主骨架：

- 作者的一句话总结；
- 生成过程、来源盘点和检查日志；
- 研发待办或接口清单；
- 按页面/状态机械展开的目录；
- 会议议程和评审问题。

## 3. 三层信息模型

### 3.1 产品主阅读层

写用户和业务可观察的事实：场景、问题、范围、用户任务、页面信息、操作、反馈、状态、异常、恢复和明确文案。默认读者不需要理解系统实现也能走通主线。

### 3.2 协作依赖层

只写会改变产品评审或跨团队责任的系统边界：谁触发、谁提供结果、谁执行、失败由谁兜底、依赖何时可用。系统名称可以出现在方案泳道、职责表和详情中的必要调用点，不在每一段反复出现。

### 3.3 研发下钻层

接口字段、错误码映射、鉴权、幂等实现、并发控制、队列、缓存、存储、算法、日志结构和数据库设计进入研发 spec。传统 PRD 只保留对应能力要求或结果约束，例如“重复点击不能产生第二次有效提交”。

使用“产品结果”替换“实现手段”：

| 不放在主阅读层 | 主阅读层写法 |
|---|---|
| CRM 幂等键阻止重复请求 | 提交中不可重复操作；重复进入不能产生第二次有效结果 |
| 接口超时和错误码统一映射 | 结果不明确时不展示成功，并提供明确恢复或人工出口 |
| 用满返回 P0 字段 | 进入可操作页面前，关键展示信息必须完整 |

## 4. 模块聚合方法

以用户任务或协作闭环作为详情模块。一个合格模块通常能独立回答：

1. 谁在什么条件下进入；
2. 用户需要看懂什么；
3. 用户可以做什么；
4. 系统如何反馈；
5. 正常结果、异常结果和恢复是什么。

页面和状态是模块内证据，不自动成为章节。同一页面承担多个独立任务时可以拆模块；多个页面共同完成一个任务时应合并说明。

为每个高风险事实指定一个主要模块。概述只保留能建立全局心智的压缩结论，验收只引用结果，不重新扩写完整规则。

## 5. 视觉层级

### 5.1 总览视觉

回答跨模块的一个问题，例如端到端协作或用户主路径。它只保留建立心智模型所需的动作、判断和结果。

### 5.2 局部视觉

紧邻详情，回答一个用户任务中的页面空间、关键状态差异或操作反馈。局部原型可以包含连续关键帧和少量连线，但不能混入全部异常网络。

### 5.3 完整核查视图

交互模型、完整状态图或全景画板用于覆盖核查。只有正文宽度下仍清楚时才内联；否则提供可缩放的独立画板或内部证据。正文用总览和局部子图解释，不让读者先解码全景网络。

## 6. 交付蓝图

视觉版或交互版在写正文前，先在工作上下文或执行包中确定：

- `primary_artifact`：传统 PRD；
- `reader_spine`：需求背景、需求目标、需求范围、产品方案、需求详情和验收标准；
- `modules`：按用户任务命名，每个高风险事实只有一个主要归属；
- `review_questions`：读者要回答的问题；
- `representation`：文字、表格、流程、泳道、状态或原型；
- `visual_role`：总览、局部或下钻；
- `placement`：视觉在正文中的准确位置；
- `term_policy`：哪些系统术语需要保留，哪些实现术语下沉；
- `validation`：同源和最终渲染如何验证。

蓝图是内部生产计划，不进入最终文档。

## 7. 反模式

- 同时交付“协作 PRD”“视觉版 PRD”和“传统 PRD”，但没有说明哪个是主文档；
- 正文每节都重复范围、一次限制、成功条件和失败出口；
- 用系统名作为用户旅程节点，或用接口状态作为页面标题；
- 把所有页面排成九宫格，却没有说明动作和结果；
- 把全部状态和迁移画成一张大图并缩进正文；
- 原型集中在文档前部，规则集中在后部，读者需要跨页匹配；
- 以“模型通过、图片生成、飞书上传成功”代替读者和渲染验收。
