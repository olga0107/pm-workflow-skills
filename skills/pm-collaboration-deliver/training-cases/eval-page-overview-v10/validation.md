# 页面交互总览能力验证

## 验证目标

验证交互型传统 PRD 能否在产品主流程与局部故事板之间，增加一张可连续追踪页面、关键页面状态、动作、条件、返回、异常与外部出口的页面交互总览；同时保证视觉聚合不丢失底层规则。

## 参考蒸馏

优秀案例采用“页面卡片作为节点、主操作从左到右、分支挂在分歧点附近、连线标动作或条件、失败与重试仍处于同一画布”的表达。此次只蒸馏信息架构和阅读方法，没有复制其具体业务、页面数量、布局尺寸或飞书语法。

## 实际案例

使用“排课冲突自主换期”交互模型进行回归：

- 14 个状态映射为 14 张页面或出口卡片；
- 31 条迁移映射为 16 条视觉连线；
- 12 条含用户动作的迁移全部可追踪；
- 11 条打开校验失败迁移、6 条提交失败迁移分别聚合为一条可视分支，但原始迁移 ID 仍保留在 overview spec 中；
- 返回、暂不调整、统一拦截、成功后的既有页面出口和人工兜底均在同一总览中出现。

## 检查结果

`check_page_interaction_overview.py`：通过。

```text
Page interaction overview passed: 14 cards, 16 connectors, 14 states, 31 transitions, 12 action transitions covered.
```

`check_prototype_plan.py` 已接入页面交互总览：多页面交互不能静默遗漏；如确实不适用，必须留下可审查原因。总览产物必须是完整覆盖、绑定同一交互模型，并通过专用 overview spec 校验。

最终 PNG 已按原始尺寸实际查看。主路径、下挂分支与外部出口可连续追踪；该资产定位为可缩放总览，正文宽度只放可读预览，局部细节继续由就近故事板承担。

## 当前结论

此次补齐的不是“再多画一张流程图”，而是新增了一个独立阅读层：

1. 产品主流程解释用户任务骨架；
2. 页面交互总览解释页面、状态与全部跳转；
3. 局部故事板解释单个需求详情中的连续反馈；
4. 完整交互模型证明底层状态和迁移无遗漏。

总览的卡片数量、分区和布局不设固定阈值，随需求结构设计；机器门槛只检查语义覆盖、映射一致性和静默遗漏。
