# 页面内容契约与 UX 原型

这份共享参考定义复杂页面需求在需求定义、分级、PRD 和 HTML 原型之间如何传递“页面应该呈现什么”。它解决的不是视觉风格问题，而是页面内容、状态和信息层级在进入设计前是否已经足够确定。

## 1. 适用范围

以下任一信号命中时，使用“页面内容契约”而不是只写页面地图或模块摘要：

- 新增页面、页面改版、单页多信息区或首页 / 主导航调整；
- 页面需要通过低保真或 UX 原型评估信息层级、首屏、密度、滚动和主任务；
- 页面包含多个独立状态域、条件信息、加载 / 空态 / 错误态或动态主操作；
- 设计、研发或测试不能依赖设计稿补齐用户可见内容；
- 文案长度、字段缺失、列表规模或多端差异会影响页面成立。

简单的局部文案、样式或既有页面中不改变信息结构的展示调整，不强制创建完整契约。

## 2. 四个概念必须分开

| 概念 | 要回答的问题 | 主要产物 |
|---|---|---|
| 页面地图 / IA | 页面、模式、信息区如何组织，用户从哪里到哪里 | 页面树、导航契约、页面结构图 |
| 页面内容契约 | 页面上具体出现哪些用户可见信息、文案和动作 | 内容清单、展示条件、缺省规则 |
| 状态组合矩阵 | 不同状态域组合时，页面哪些区块出现、变化或不可用 | 页面 × 状态 × 信息区矩阵 |
| UX 原型 | 上述内容如何在视窗内排列、滚动、切换和反馈 | 页面状态原型、覆盖台账 |

信息架构不是内容清单的替代品，原型也不是内容契约的主源。四者需要通过稳定 ID 互相追溯。

## 3. 页面内容契约字段

每个页面 / 信息区的用户可见内容至少记录以下字段：

| 字段 | 说明 |
|---|---|
| `CONTENT-ID` | 稳定追溯 ID，例如 `LEARN-LIVE-TITLE` |
| 页面 / 信息区 | 所属 Page、Section 或组件 |
| 用户可见内容 | 静态标题、字段、状态文案、按钮、提示、placeholder 或反馈 |
| 内容类型 | 静态信息 / 动态数据 / 条件信息 / 操作反馈 |
| 展示条件 | 什么状态、角色、数据或动作下出现 |
| 缺省与异常 | 缺失、空、加载、失败、过期时显示什么，是否可恢复 |
| 优先级 | P0 / P1；影响首屏或主任务时应明确 |
| 长度 / 密度约束 | 行数、截断、数量、列表规模或代表性数据要求 |
| 允许动作 | 用户能做什么，按钮目标和不可用原因 |
| 状态影响 | 哪些状态域改变它，哪些状态域独立于它 |
| 原型 / 验收关联 | 对应原型故事、功能、规则或验收 ID |
| 决策状态 | 已确认 / 假设 / 待确认；待确认必须写负责人、时间和阻塞影响 |

“用户可见内容”必须包含静态文本，不得只列接口字段、数据对象或“按设计稿展示”。未确认的文案可以标记为待确认，但不能用无语义的“标题”“按钮”“暂无数据”等通用占位掩盖缺口。

## 4. 页面状态组合的表达方式

不要把所有状态域做成笛卡尔积，也不要只画一个“正常态”。先区分状态域：

- 全局状态：登录、权限、版本、网络；
- 页面状态：首次进入、模式、筛选或搜索上下文；
- 信息区状态：加载、成功、空、失败、刷新中；
- 业务状态：课程、订单、直播、任务或权益状态；
- 组件状态：选中、展开、校验、提交中、不可用。

然后记录每个代表组合：

| 组合 ID | 页面状态 | 关键状态域 | 用户任务 | 必须出现的信息区 | 主动作 / 反馈 | 原型策略 |
|---|---|---|---|---|---|---|
| STORY-01 | 首次进入 | 页面成功 + 有数据 | 开始主任务 | 页面壳层、主信息区、主操作 | 进入下一页 | 必须成图 |
| STORY-02 | 页面成功 + 无结果 | 空态 | 理解为什么没有结果 | 空态说明、恢复 / 替代入口 | 去探索 / 重试 | 必须成图或有等价规则证据 |
| STORY-03 | 局部失败 | 信息区错误 | 恢复当前任务 | 错误原因、重试或返回 | 重试 | 必须成图 |

原型只需要覆盖能证明关键任务、页面层级、异常和端差异的代表组合；豁免组合必须有状态架构、规则和验收依据，不能被误画成已经验证的最终页面。

## 5. 内容完整性的 UX 原型标准

当交付目标是“可评估页面效果”的 UX 原型时，原型必须满足：

1. 所有 P0 信息区均有可辨识且可滚动到达的区域；
2. 当前故事中的所有用户可见静态文案、动态字段、状态标签、动作、反馈和必要占位均来自内容契约；
3. 页面层级、首屏、滚动 / 固定区域、信息密度和长文本约束可被评审；
4. 加载、空、错误、权限和恢复路径至少覆盖关键代表状态；
5. 代表性数据足以暴露长标题、多项列表、缺图、缺字段和多状态并存问题；
6. 原型中的文字不能临时创作内部说明、追溯 ID、接口字段或没有来源的业务文案；
7. 探索方案、评审稿和基线稿必须明确区分；未决策方案不得作为设计交接基线；
8. 内容契约未完成时，HTML 应报告阻塞或待确认，不得用“详见设计稿”作为完成条件。

UX 原型不等于视觉设计稿：它需要内容和交互结果足够真实，但不替代品牌视觉、最终组件样式和设计 token。

## 6. 跨工作流交接

| 阶段 | 负责什么 | 交给下一阶段什么 |
|---|---|---|
| 需求定义 | 确认页面为何改变、用户任务、评审目标和信息不确定性 | 页面是否需要内容完整型 UX 原型的线索 |
| 需求分级 | 判断体验复杂度和最低交付门槛，不写页面规格 | 页面内容契约、状态组合和原型覆盖是否必填 |
| PRD 编写 | 建立 IA、内容契约、状态架构、页面构成、规则和验收 | 可编译的页面 × 状态 × 内容中间层 |
| HTML 编译 | 只按主源生成故事、SVG、覆盖台账和阅读版 | 可评审的 UX 原型和内容覆盖结果 |
| 设计交接 | 在已确认内容和结构上完成视觉表达 | 不自行补齐缺失业务信息 |
| 研发 / 测试 | 按内容契约、状态、行为和验收实现与验证 | 不把字段、接口或设计稿当作页面内容主源 |

发现内容或状态逻辑缺口时，应回退到 `pm-prd-write`，而不是在 HTML、设计稿或研发实现中静默补齐。
