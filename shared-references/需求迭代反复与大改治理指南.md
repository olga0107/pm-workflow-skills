# 需求迭代反复与方案大改治理指南

> 这是一份跨 skill 的治理协议，适用于需求在梳理、PRD、技术方案、实现、验证或发布阶段反复改口径，甚至从“加一个展示能力”演变为规则、数据模型和结算链路重构的情况。它不替代需求定义、分级、PRD、质量审计或发布说明，而是规定何时回退、哪些结论失效、如何重新收口。

## 1. 为什么需要这份协议

复杂迭代的主要风险不是“讨论次数多”，而是**上游业务原则发生变化后，下游仍沿用旧版本**。典型表现包括：

- 用户先提出一个页面能力，后续发现真正难点是历史事实、状态时序、归属或结算规则；
- 为解决展示问题引入新读模型、迁移、双写或异步任务，但没有先评估是否可以收敛源头规则；
- PRD / Spec 已经展开，用户又改变锁定时点、历史边界或是否重算，导致前文、验收和实现依赖不再有效；
- 技术预验证、测试数据、UI 目测和真实用户验收被混在“已验证”里；
- 代码和文档完成后，才发现活动编辑、权限、运营后台、旧数据或发布状态仍保留旧口径。

本协议的目标是：**让每次大改都成为一次受控的版本切换，而不是在旧文档上继续叠加补丁。**

每个可留档的协作产物还必须遵守[产物修订记录与版本追溯规范](./产物修订记录与版本追溯规范.md)：版本台账记录跨文档的业务决策变化，修订记录记录每份产物自身的变化，两者不能互相替代。

## 2. 先判断是否属于“大改”

将变更分成五类：

| 类型 | 判断标准 | 默认动作 |
|---|---|---|
| 局部表达调整 | 不改变业务规则、数据事实、范围、权限、验收结果 | 在当前产物修订，保留原审计有效性（若不影响审计对象） |
| 产品规则调整 | 改变谁能做什么、何时生效、何时锁定、是否重算、历史是否追溯 | 回到需求定义，更新规则台账和决策记录；重新分级 |
| 架构 / 数据模型调整 | 新增或删除事实源、读模型、迁移、双写、索引、批任务、事务边界 | 先做源头规则再评估与技术预验证，再重写 PRD / Spec / 验收 |
| 范围 / 风险调整 | 新增角色、端、后台、生产数据、资金 / 权益、跨模块联动或不可快速回滚影响 | 重新分级；必要时升档，原交付门禁失效 |
| 验收 / 发布事实更正 | 测试结果、真实 UI、生产版本、上线日期或文档状态被更正 | 关闭旧结论，回到相应阶段补证据；不得用文案掩盖状态差异 |

只要命中后三类之一，必须视为**重大变更**。不能只在 PRD 末尾追加“补充说明”，也不能继续沿用旧的 `ready`、等级、审计 `PASS` 或“可提审”结论。

## 3. 版本状态机与回退规则

每个复杂需求都应显式标记当前版本所处阶段：

```text
探索中 → 业务决策待确认 → 决策冻结 → 分级完成 → PRD/Spec 展开
       ↘ 源头规则重评估 ↗             ↓
实现中 → 技术预验证 / 方案修正 → 验收中 → 发布收尾 → 已归档
```

### 3.1 版本冻结条件

只有同时满足以下条件，才能把版本标记为“决策冻结”：

- 问题、目标、一级范围、非目标和主要角色已确认；
- 规则台账中旧规则、新规则、明确不变项、生效边界和历史处理都有来源状态；
- 关键时间点、归属原则、重算与不重算边界已确认；
- 已评估“改源头规则是否能减少技术复杂度”，并记录未采用方案及原因；
- 主要未知已区分为产品决策、技术可行性、数据证据、页面规格或测试证据，不再混用“待确认”；
- 负责人明确接受当前复杂度、历史取舍和剩余风险。

### 3.2 何时必须回退

| 新信息 / 新意见 | 回退到 | 必须作废或重审的产物 |
|---|---|---|
| 改变锁定点、归属主体、评价 / 结算重算或历史范围 | 需求定义 | 分级、PRD、Spec、验收、审计中受影响部分 |
| 发现原规则过宽导致复杂度，准备收敛源头 | 需求定义 + 源头规则重评估 | 原数据模型、迁移、双写和任务设计 |
| 发现新增写入、异步、并发、迁移或外部依赖 | 需求分级 + 技术预验证 | 原等级、实现门禁、回滚和观测要求 |
| 用户改变页面布局、状态展示或字段语义，但业务事实不变 | PRD / 页面内容契约 | 受影响 HTML、设计稿、验收截图 |
| 测试 / UI 验证发现实现与需求不一致 | 实现 / PRD 对账 | “已验证”结论、验收状态和发布资格 |
| 生产版本、上线日期或角色影响发生更正 | 发布收尾 | 更新说明、需求包状态、稳定知识和索引 |

回退时必须在版本记录中写明：变更原因、原结论、现结论、受影响范围、作废证据、重新验证条件。旧文档可以保留作历史，但必须标注“已被版本 X 取代”。

## 4. 需求定义阶段的“复杂度源头复盘”

当用户质疑“是不是设计得太复杂”时，不能直接在现有技术方案上做删减。按以下顺序复盘：

1. **重述业务不变量**：到底必须保证什么，例如历史归属不可被当前关系改写、已封账奖励不追溯、用户不能看到半成功结果。
2. **检查源头规则**：活动是否允许关键字段在过晚节点编辑、关系是否允许在结束后改变、评价是否允许无限期修改、取消是否存在多个事实源。
3. **比较收敛方案**：用更早锁定、取消重建、单一事实源、分层结论、代际分流等方式减少状态组合。
4. **再判断是否需要复杂技术**：只有业务不变量仍需要时，才引入快照、读模型、迁移、事务、队列或补偿。
5. **把取舍写回产品规则**：源头规则一旦收敛，必须同步更新角色影响、页面状态、编辑权限、验收和更新说明。

输出至少包含：

| 问题 | 当前复杂度来源 | 可收敛的源头规则 | 采用 / 不采用 | 对范围与风险的影响 |
|---|---|---|---|---|
|  |  |  |  |  |

禁止把“为了兼容所有历史情况，所以新增一套事实源”作为默认答案；先确认历史是否真的需要逐条可追溯、是否可以基线展示、是否可以新旧代际分流。

## 5. 方案决策记录：每轮只推进一个层级

复杂迭代应把问题分成四层，避免一轮同时讨论页面、业务、架构和代码：

1. **业务原则层**：谁获得结果、何时冻结、哪些变更允许发生、历史是否追溯；
2. **产品行为层**：用户看到什么、哪些状态、哪些角色能操作、哪些入口受限；
3. **技术方案层**：事实源、索引、事务、任务、迁移和失败恢复；
4. **验证交付层**：静态检查、技术预验证、接口结果、真实 UI、用户验收、发布状态。

每轮输出“已确认 / 待确认 / 不再讨论 / 下游处理”的短表。用户改变上层结论时，先停止下层展开；不要用下层细节反向逼迫用户接受尚未确认的业务规则。

## 6. 技术预验证应前置且必须有结论

对于以下事项，不能等实现完成后才首次验证：

- 数据库是否支持目标查询、排序和游标分页，扫描量是否可控；
- 事务 / 并发是否能保证活动结论与多主体累计指标不半成功；
- 定时任务、重试、超时、幂等、积压和失败恢复是否满足产品语义；
- 旧数据、历史基线、新旧代际或字段兼容是否能按非目标落地；
- 关键入口是否存在绕过新锁定规则的前端 / 后端路径。

预验证结论必须写成：**已验证事实、验证方法、限制、仍需实现阶段验证的内容、若失败的替代方案**。架构可行不等于代码已实现；静态检查通过不等于运行链路已验证。

## 7. 验证交付要拆成四种证据

不要用一个“测试通过”覆盖不同证据：

| 证据层 | 证明什么 | 典型证据 |
|---|---|---|
| 静态证据 | 代码 / 文档能被解析，基本规则未明显违例 | lint、类型 / 语法检查、链接检查、diff |
| 运行证据 | 云函数 / 接口 / 任务在目标环境按预期返回 | 真实请求结果、日志、任务状态、索引 explain |
| 视觉证据 | 用户实际看到的页面状态与布局符合预期 | 真机 / 开发者工具截图、窄屏 / 长标题 / 空态 / 错误态 |
| 业务验收证据 | 负责人确认体验和规则达到目标 | 逐条验收记录、已确认的调整项 |

“没有运行证据”时，不能写“已验证”；“没有视觉证据”时，不能写“UI 已验收”；用户提出 UI 修正后，原视觉证据应标为过期并重新检查。

## 8. 测试数据、部署与工具协作

涉及测试数据或需要用户部署 / 点击操作时，必须维护一个最小测试运行卡：

- 环境、部署版本、操作者和目标账号；
- 唯一 `batchId` / 数据前缀、场景覆盖、预期结果；
- 当前已执行步骤、返回结果和下一步依赖；
- 超时、部分成功、重复执行和清理策略；
- 清理前不得宣称测试闭环，清理后保留删除统计和失败项。

当工具上下文不稳定时，应先报告“尚未执行”，不要反复盲调或把准备好的命令当成结果。每次重新部署后，应记录部署版本与需要重跑的最小验证集合。

## 9. 收尾时必须做“规则—实现—页面—文档—发布”对账

发版前不要只复查新增功能；至少逐项回答：

- 源头规则收敛后，创建、编辑、取消、结束、评价、权限和后台入口是否仍兼容；
- 页面禁用态、状态色、标题、时间格式、身份标签、结算结论和分页是否与最终语义一致；
- 活动明细与考核记录是否各自有清晰的分页 / 加载更多，不把两种列表混成一套；
- 需求定义、PRD、Spec、验收、稳定知识、更新说明和索引是否使用同一最终版本；
- 交付状态、验收状态、发布状态、版本号和发布日期是否分别有事实依据。

收尾输出应至少包含：已修复项、未修复项、残余风险、发布前动作、发布后观察、文档同步清单和可回退方案。

## 10. 每轮协作都要留下产物修订记录

复杂需求不应只有一张“迭代版本与决策台账”。需求定义、分级卡、PRD、HTML、审计报告、验收清单、更新说明和上线观察都要在自身文档中保留修订记录。每轮有明确结果的协作修改后立即追加一行，至少说明：

- 版本和日期；
- 触发原因 / 协作阶段；
- 本次主要变化；
- 受影响章节、下游产物和失效证据；
- 确认人 / 责任人；
- 当前状态。

纯排版和错别字可不记；涉及规则、范围、状态、验证、审计、发布或角色影响的变化必须记。上游版本变化时，相关下游修订记录必须同步更新，旧版本和旧证据标记为 `superseded` / `stale`，不能只改正文不留历史。

## 11. 可复用的最小产物

命中重大变更时，建议在需求包中新增 `迭代版本与决策台账.md`，至少包含：

| 版本 | 时间 | 触发原因 | 业务决策变化 | 技术 / 范围影响 | 受影响产物 | 状态 |
|---|---|---|---|---|---|---|
| V0 |  | 初始假设 |  |  |  | superseded / active |

以及一张“验证状态卡”：

| 验证项 | 证据类型 | 环境 / 版本 | 结果 | 限制 / 下一步 | 状态 |
|---|---|---|---|---|---|
|  | static / runtime / visual / acceptance |  |  |  | pending / passed / stale |

这两张表能把“方案反复”和“证据反复”分开，避免读者只看到最后版本而无法理解为什么改、哪些结论已经失效。
