# 产品交付质量框架

> 这不是另一份写作模板，而是所有产品工作产物的共同质量协议。它解决的问题是：产出“看起来完整”不等于可以安全交给下一环节。

## 1. 两层完成定义

每个产物必须区分：

1. **生成完成**：已经按对应 skill 的方法、边界和输出结构写出。
2. **质量通过**：已经经过独立视角的质量审计，关键事实、逻辑、覆盖、追溯和交接风险达到门槛。

`完成标准` 只能证明生成完成，不能单独证明质量通过。未经过审计时，必须标记为“未审计”，不能写成“已确认”“可直接交付”或“可直接进入下一环节”。

## 2. 六个质量维度

| 维度 | 要回答的问题 | 常见证据 |
|---|---|---|
| C 上下文充分性 | 影响本阶段判断的背景、目标、约束和证据是否够用？ | 事实清单、材料索引、数据口径、项目文档、缺口清单 |
| L 逻辑有效性 | 事实能否推出问题，问题能否支撑目标，目标能否支撑方向和范围？ | 因果链、方案比较、取舍、反例、决策记录 |
| K 覆盖完整性 | 相关角色、场景、状态、异常、约束、验收和交接是否覆盖？ | 覆盖矩阵、页面 × 状态、风险扫描、验收矩阵 |
| T 可追溯性 | 每个关键结论、规则和原型是否能回到来源，并能反向定位影响？ | 事实/结论编号、章节定位、来源链接、traceability matrix |
| O 可执行性 | 下游人员能否据此实现、测试、发布、观察或复盘？ | 责任人、输入输出、验收、回滚、监控、待决事项 |
| U 不确定性校准 | 已确认、推断、假设、未知和待确认是否明确区分，是否存在无依据的确定语气？ | 证据等级、假设台账、阻塞项、风险和条件 |

不要用维度总分抵消硬缺陷。例如，文档写得很完整但关键权限规则未知，仍然不能通过交付门禁。

## 3. 证据状态

对影响决策或实现的内容统一标记：

- `confirmed`：有明确来源或负责人确认；
- `inferred`：由多个事实推导出的判断，需写出推导依据；
- `assumed`：为了继续推进暂时采用的假设，必须写出验证方式或失效条件；
- `unknown`：当前不知道，不能用泛化文案或设计稿掩盖；
- `blocked`：未知项会改变当前阶段的关键结论，必须回退或请求确认。

## 4. 审计结果

统一使用以下三种结果：

- **PASS**：无未解决的 Blocker / Major，达到本阶段交接门槛；
- **PASS_WITH_CONDITIONS**：无 Blocker，但存在已登记的 Major；每项有负责人、处理动作和截止条件；
- **BLOCKED**：存在 Blocker，或关键上下文不足，不能安全交给下一环节。

严重度：

- **Blocker**：会导致方向、分级、核心业务规则、权限/资金/隐私、关键状态、主要路径或交付物真实性错误；
- **Major**：会导致明显返工、下游无法执行、重要场景遗漏或结论可信度不足；
- **Minor**：不影响当前决策和执行，但会降低可读性、效率或维护性。

## 5. 评分只是诊断，不是放行依据

每个维度可用 `0 / 1 / 2 / N/A` 记录：

- `0`：缺失、错误或无法判断；
- `1`：部分满足，存在已知缺口；
- `2`：满足当前阶段门槛；
- `N/A`：确实不适用，并说明为什么不是遗漏。

放行规则：

1. 任一 Blocker 直接 `BLOCKED`；
2. 关键维度为 `0` 直接 `BLOCKED`；
3. 存在 Major 时，必须登记责任人和完成条件；没有责任和条件不得 `PASS_WITH_CONDITIONS`；
4. 所有 N/A 必须有理由，不能用来逃避检查；
5. 审计结论必须引用实际位置或证据，不能只给“感觉完整”。

## 6. 阶段门槛

| 阶段 | 必查维度 | 关键放行问题 |
|---|---|---|
| 研究 / 竞品 / 指标 | C、T、U、L | 材料、样本、数据口径和来源是否足以支持结论？反例和局限是否被保留？ |
| 需求定义 | C、L、K、U | 问题成立吗？方向真的被选择了吗？一级范围和重大约束是否足以进入分级？ |
| 需求分级 | C、L、K、O、U | 是否完整扫描红线？风险与等级是否匹配？路由和门禁是否足够？ |
| PRD / 交付规格 | C、L、K、T、O、U | 角色、场景、状态、权限、异常、验收、发布和指标能否被实现和测试？ |
| HTML / 协作原型 | K、T、O、U | 是否忠实编译源 PRD？页面状态、用户可见内容、原型和阅读交互是否真实可核验？ |
| 更新 / 复盘 | C、T、L、O、U | 是否只传播已确认事实？变化、影响、数据和行动是否可追溯且不越界？ |

## 7. 最小追溯矩阵

复杂或高风险产物至少维护以下列；简单产物可以用短表替代，但不能省略关系：

| ID | 需要证明/交付的事项 | 来源/证据 | 产物位置 | 状态 | 下游动作 |
|---|---|---|---|---|---|
| Q-001 | 关键事项 | F-001 / D-001 / 用户确认 | 章节或段落 | confirmed / inferred / assumed / unknown | 实现、验证、补证据或回退 |

最少覆盖：

- 需求定义：事实 → 问题 → 目标 → 方向 → 范围；
- 分级：风险事实 → 红线命中 → 等级 → 交付门禁；
- PRD：目标/范围 → 功能/规则/状态 → 验收/发布/指标；
- HTML：PRD 来源 → 阅读区/状态故事/原型 → 覆盖或豁免；
- 复盘：指标口径 → 事实变化 → 假设 → 行动。

## 8. 审计的反自证原则

同一个模型可以连续完成生成和审计，但必须分成独立阶段：

1. 先只做审计，禁止顺手改写；
2. 逐条报告缺口、矛盾、无来源判断和下游风险；
3. 再执行修复；
4. 修复后重新审计受影响维度；
5. 仍有未知时保留未知，不为了得到 PASS 而补造事实。

“我已经检查过了”“整体看起来没问题”不属于质量证据。

## 9. 触发与留档策略

质量审计按交付意图触发，不是每次草稿都强制审计：

| 协作意图 | 是否自动审计 | 默认表现 |
|---|---|---|
| 讨论、探索、草稿、脑暴 | 否 | 允许快速迭代，但标记“未审计” |
| 产出 ready、建议定级、交给设计 / 研发 / 测试 / 运营 | 是 | 原 skill 生成后自动调用 `pm-quality-audit`，审计结论跟随本次输出 |
| 用户明确说“只先给初稿” | 否 | 不触发审计，但不能宣称可交接 |
| 用户明确要求审计、复核、验收或留档 | 是 | 使用 `audit-only` 或 `audit-and-repair`，按要求输出报告 |

自动审计的最小行为是：原 skill 先完成产物，再调用 `pm-quality-audit audit-only`；只有审计通过或用户明确接受条件，才可以把状态写为“可交接”。审计 skill 不再递归调用自己。

审计报告有两种沉淀方式：

1. **对话沉淀**：默认返回结构化审计报告，适合短期讨论；
2. **文件沉淀**：用户要求“留档 / 生成报告 / 作为交接附件”时，在当前项目根目录的 `quality-audits/` 下生成 Markdown 报告，并记录被审计产物路径、版本 / 时间、审计结论和 QA-ID。

审计报告是某个版本的质量证据，不是新的事实源。被审计产物发生影响内容的修改后，原报告自动视为过期，必须重新审计。
