# pm-quality-audit

把“已经生成”与“可以交付”分开。这个 skill 是跨阶段的质量审计层，不负责重新写需求、PRD 或 HTML；默认先发现问题，再决定是否需要回到原 skill 修复。

## 优先读取

1. [产品交付质量框架](../../shared-references/产品交付质量框架.md)
2. 被审计产物及其上游输入、来源材料和交接契约
3. 目标阶段对应的 skill、模板、示例和项目规则
4. 如为 HTML，读取源 PRD、页面内容契约、原型覆盖计划和实际渲染结果
5. 如为高风险需求，读取分级矩阵、项目画像、研发/测试/发布门禁

## 工作边界

负责：

- 判断本阶段所需上下文是否足够，并把缺口分为可查事实、需补证据、需产品决策、需规格展开和需研发实现；
- 检查关键结论的事实依据、推导链、反例、边界和不确定性标记；
- 按阶段建立覆盖矩阵和最小追溯矩阵，检查上下游是否断链；
- 检查跨章节、跨产物和源文档与派生物的一致性；
- 输出 Blocker / Major / Minor、证据定位、影响、修复建议和交接结论；
- 修复后重新审计受影响范围，并记录残余风险。

不负责：

- 直接替代原 skill 重新做产品方向、风险定级、PRD 规格或 HTML 编译；
- 为了让文档通过而补造用户、业务、数据、竞品或技术事实；
- 用主观总分掩盖关键硬缺陷；
- 把未确认的建议改写成已确认结论；
- 在没有实际浏览器渲染证据时声称 HTML 已通过视觉验收。

## 审计模式

根据用户要求选择一种；未指定时默认“审计并给修复计划”，不直接改原文：

- `audit-only`：只审计，保留原产物；
- `audit-and-repair`：先输出审计发现，再回到原 skill 修复，最后复审；
- `calibration`：对多个案例归类缺陷，判断应改 skill、模板、共享规则还是项目上下文，并生成回归案例建议。

原 skill 在“交接 / ready”场景下可以自动调用本 skill，但本 skill 不递归调用自己。讨论、草稿和脑暴默认不自动审计，除非用户明确要求。

## 工作流程

### 1. 确认审计对象与放行目标

明确：产物类型、所处阶段、预期下游、输入版本、是否高风险、是否要求设计前评估页面效果。若产物和上游版本不明，先标记为 `BLOCKED`，不要假定“当前这份”就是正确版本。

### 2. 建立上下文充分性账本

把影响判断的内容分成：

- 已确认事实；
- 可由项目资料直接查到的事实；
- 需要研究 / 竞品 / 指标补证的内容；
- 需要产品负责人决定的内容；
- 只能由 PRD / spec / 测试展开的内容；
- 当前未知但不阻塞的内容。

对会改变方向、等级、核心规则、责任或上线安全的未知项，标记为 `Blocker` 或 `blocked`。

### 3. 做对抗式检查

至少执行以下检查，不要只顺着正文复述：

1. **反事实检查**：如果关键假设不成立，问题、方向或等级是否仍成立？
2. **遗漏检查**：谁没有被覆盖？哪个主任务、异常、状态、权限、历史路径或回滚路径没有被写出？
3. **矛盾检查**：目标、范围、规则、状态、验收、指标、原型和发布要求是否互相冲突？
4. **过度确定检查**：哪些句子把推断、建议或未知写成了事实？
5. **下游可执行检查**：设计、研发、测试、运营或数据人员是否能据此采取动作并判断完成？
6. **放大检查**：用户量、调用量、失败率或地区扩大 10 倍时，当前规则、人工流程和服务承诺是否仍成立？

### 4. 建立阶段覆盖与追溯矩阵

只列与当前阶段相关的事项，不为填表虚构维度。每个关键事项至少有来源、产物位置、状态和下游动作；没有来源的结论必须降级为假设或未知。

### 5. 输出分级缺陷

每条发现必须包含：

- `QA-ID`；
- 严重度；
- 维度（C/L/K/T/O/U）；
- 产物位置；
- 证据或缺失证据；
- 为什么会影响当前阶段或下游；
- 修复动作；
- 修复责任方；
- 放行条件或截止条件。

### 6. 给出放行结论

按共享质量框架输出 `PASS`、`PASS_WITH_CONDITIONS` 或 `BLOCKED`。结论不能只由平均分决定：任何 Blocker 直接阻塞；Major 只有在有责任人和明确完成条件时才可条件放行。

### 7. 修复与复审

`audit-and-repair` 模式必须遵循“先审计 → 再修复 → 受影响维度复审”。修复后若仍有未知，保留其状态、责任和验证计划，不把它强行改成已确认。

## 阶段专用检查重点

### 需求定义

- 背景事实能否推出问题，问题是否说明影响对象、场景、程度和不处理损失；
- 目标、方向、一级范围和非目标是否一一对应；
- 是否比较真实可选方向并写明取舍和临界条件；
- 主要角色、入口、主任务、关键路径和重大约束是否足以进入分级；
- 证据缺口、决策缺口、PRD 规格缺口和研发实现缺口是否分开。

### 需求分级

- 是否完整扫描资金、身份、隐私、权益、核心链路、数据写入、状态机、AI 自动化、外部依赖、全局配置、生产数据和不可快速回滚红线；
- 等级是否由真实影响和后果决定，而不是由代码量、页面数量或“AI 能实现”决定；
- AI Coding、PRD、spec、QA、灰度、回滚和观察门禁是否与风险匹配；
- 信息不足时是否明确暂定等级和补齐条件，而非假装精确。

### PRD / 交付规格

- 需求定义和分级是否仍是单一决策来源，PRD 有没有静默改变方向或范围；
- 页面、流程、角色、权限、状态、规则、异常、历史兼容、系统能力、验收、发布、回滚、监控和指标是否按风险覆盖；
- P0 功能是否能由用户动作、系统结果和验收条件闭环；
- 每个重要规则是否能追溯到目标、约束或决策；
- 接口字段、算法、队列、存储等实现细节是否越过 PRD/spec 边界。

### HTML / 协作原型

- HTML 是否忠实编译源 PRD，没有第二套业务规则或无依据文案；
- 页面 × 状态、用户可见内容、端形态、滚动 / 固定区域和代表组合是否按计划覆盖；
- 图、流程、正文、验收和状态切换是否一致；
- 是否真的进行浏览器渲染后的首屏、窄屏、长页、溢出、导航和交互验收；
- 未成图组合是否有规则或流程依据，是否误画成可操作控件。

## 审计报告沉淀

默认在对话中返回结构化《质量审计报告》。当用户要求“留档”“生成报告”“作为交接附件”，或当前工作正在维护项目文档时，将同一报告写入当前项目根目录的 `quality-audits/`：

```text
quality-audits/<日期>-<阶段>-quality-audit.md
```

文件名冲突时追加序号，不覆盖历史报告。报告必须记录：被审计产物路径、输入版本或时间、审计模式、结论、QA-ID、修复条件和残余风险。审计对象发生影响内容的修改后，原报告标记为过期，不得继续作为放行证据。

审计报告不是新的业务事实源，也不替代原需求、PRD 或 HTML；它只记录某个版本是否达到交接门槛。

## 完成标准

- 审计对象、版本、阶段和预期下游明确；
- 关键上下文、来源、假设和未知项有账本；
- 至少完成反事实、遗漏、矛盾、过度确定和下游可执行检查；
- 每个 Blocker / Major 都有证据定位、影响和修复条件；
- 结论符合共享质量框架，未用平均分掩盖硬缺陷；
- 未经实际渲染或真实来源验证，不声称 HTML、数据或外部事实已通过；
- `audit-and-repair` 已完成修复后的受影响范围复审；
- 需要留档时，报告已写入 `quality-audits/`，并记录被审计版本；
- 报告能够让下一环节知道“是否可以接、还缺什么、谁来补、补到什么程度”。
