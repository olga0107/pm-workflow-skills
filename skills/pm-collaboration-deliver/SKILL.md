# pm-collaboration-deliver

把稳定的正式 PRD 编译成一份简洁、完整、视觉清楚的传统产品文档。正式 PRD 是高密度、可追溯、可供 AI 和执行团队继续消费的产品事实源；本 skill 是面向人的承接层，负责读者主线、信息分层、页面理解、交互表达、交付平台和质量门槛。

## 先锁定交付物

默认只交付一份传统 PRD 主文档。除非用户明确要求，不把协作简报、评审讲稿、执行包或研发交接表混进主文档，也不并行生成第二种主阅读稿。

先锁定主文档的交付面和文件格式。用户或项目已有约定时遵循约定；未指定的本地交付默认使用 Markdown，以便保留链接、图源和自动检查。只有用户明确要求、现有团队模板要求或目标平台确实需要时才生成 DOCX/PDF；此时调用对应文档技能并完成最终渲染检查，不能用未渲染的办公文件替代主文档验收。

阅读版、视觉版、交互版是同一主文档的内容深度，不是三种文档模板：

| 路径 | 适用情况 | 在传统 PRD 中增加什么 |
|---|---|---|
| 阅读版 | 单点变化、规则简单、无复杂迁移 | 聚合正文与必要小表 |
| 视觉版 | 顺序、交接、条件、状态或空间关系用图更清楚 | 回答独立问题的流程、关系图或局部原型 |
| 交互版 | 多页面、多状态、异步结果、返回/取消/重进或高风险恢复 | 完整交互模型证据 + 产品主流程 + 页面交互总览 + 局部交互故事板 |

不要按页面数、节点数或固定套餐选路径。复杂度来自读者必须理解的关系和错误代价。

无论选择哪条路径，都不以“保留上游章节”为完成标准。必须把正式 PRD 中分散在一页结论、FR、RULE、状态矩阵和 AC 的同一用户任务重新聚合；若成稿仍要求读者理解上游 ID、参数、路由或系统实现才能走通，说明转译尚未完成。

## 优先读取

1. 始终完整读取正式 PRD、[交付物架构与信息分层](./references/交付物架构与信息分层.md)和[传统 PRD 转译与模板](./references/传统PRD转译与模板.md)。
2. 需要任何视觉时读取[图形与原型表达](./references/图形与原型表达.md)。
3. 需要生成、承接或评审页面原型，或输入中包含截图、设计稿、现有页面时，读取[原型设计与截图承接](./references/原型设计与截图承接.md)。
4. 进入交互版时读取[交互型 PRD 与状态模型](./references/交互型PRD与状态模型.md)。
5. 存在多个相互依赖资产、高风险规则或正式门禁时读取[执行层工作流与门槛](./references/执行层工作流与门槛.md)。
6. 成稿后读取[质量检查](./references/质量检查.md)，执行当前路径的检查。
7. 只有用户要求创建、更新或验收飞书文档时才读取[飞书发布与渲染](./references/飞书发布与渲染.md)。

## 不可破坏的契约

- 只编译已确认事实；不得新增入口、权限、页面行为、业务状态、结果或恢复规则。
- 传统 PRD 是唯一主阅读面；内部模型、来源映射、检查日志和生成过程不得污染正文。
- 主文档遵循“需求背景 → 需求目标 → 需求范围 → 产品方案 → 需求详情 → 验收标准”的传统语义链；简单需求可以合并小节，条件章节按需出现，但不能丢失核心语义或改写成作者总结、协作简报目录。
- 每个高风险事实只有一个主要正文归宿；其他位置引用、概括或下钻。
- 正式 PRD 已写明风险、待确认或关键决策时，可在正文前加不参与编号的“评审关注”区块：逐条摘取并标注来源章节/ID，源文档没有则整块省略，不生成模型自己的总结。
- 产品主阅读层使用用户和业务语言；系统职责集中在方案流程或协作下钻，接口字段、幂等、队列、存储和算法进入研发 spec。
- 每个视觉回答一个明确读者问题；不得用一张图同时承担跨系统流程、用户动线、页面空间和完整状态覆盖。
- 结构示意不得伪装成最终设计；正式设计、现状截图和已确认组件优先于新画低保真。
- 原型呈现的是产品经理已决定的方案：真实文案、具体示例数据、已决定的按钮文案与状态（含禁用、加载、错误）。业务规则用用户可见的界面元素表达（横幅、禁用按钮、弹层、toast），禁止在页面里画"待定/占位/此处放xx"式虚线注释框——未决定的问题回到上游或写进正文缺口，不画进原型。
- 截图只能证明可观察的现状或视觉参考，不能单独证明隐藏状态、动作结果、权限和恢复；产品语义与视觉上下文必须分别判断。
- 必须查看最终交付平台中的正文和视觉；文件存在、脚本通过或上传成功都不等于可交付。

## 主工作流

```text
正式 PRD
→ 事实稳定性与边界检查
→ 传统 PRD 读者主线和模块归属
→ 视觉问题与表达路由
→ 按用户任务生产正文和局部资产
→ 压缩重复并下沉内部术语
→ 同源、交互和最终阅读检查
→ 按需发布飞书并回看
```

### 1. 确认事实稳定

归并背景、决策、范围、FR、规则、状态、AC 和数据中的同一事实。再登记正式设计、现状截图和视觉参考的证据角色。将缺口分为两类：会改变入口、权限、用户可见信息、主操作、状态、结果、恢复、时间或数据口径的阻断缺口，停止受影响模块并返回上游；不改变当前产品行为、只影响后续设计或实现细化的非阻断缺口，可以继续稳定模块，但必须写清缺什么、影响什么、由谁在何时补齐。不要把所有缺口统一命名为“评审待确认”，也不要让读者替产品决定已确认方案。

### 2. 建立读者主线

使用 `assets/traditional-product-document-template.md` 规划主文档，先确定：

- 当前事实、具体问题和希望改变的用户或业务状态；
- 本期范围、非目标、总体方案与保持不变项；
- 用户如何从入口走到结果；
- 哪些条件改变结果；
- 详情按哪些内聚用户任务展开。

章节名可以贴合业务，但必须保留传统语义。不要从“一句话方案”“评审重点”“研发下钻”直接起稿。

在展开正文前先完成一次人类化转译：把接口、路由、参数、状态枚举和系统动作改写成用户入口、页面表现、可用操作、反馈和结果；只在精确验收或跨团队责任确实需要时保留技术名，并集中放到下钻位置。轻量需求优先合并章节、使用“当前—调整后—保持不变”和一张就近视觉；不得因为模板完整而把短需求扩写成长文档。

### 3. 建立视觉问题

先问读者要理解什么，再选表达：

- 谁在什么时机交接：泳道或时序；
- 用户如何完成任务：产品动线；
- 条件如何得到结果：决策表；
- 单一对象如何迁移：状态图；
- 页面信息、操作和反馈在哪里：局部原型或状态对比。

产品主流程先建立任务心智，页面交互总览再把关键页面状态、页面内动作、跳转条件、返回和结果出口连成一张可追踪的页面地图，局部图紧邻详情。页面交互总览中的可见页面卡片必须像缩略页面：至少能看出用户任务、关键信息、主次操作和当前反馈；只有标题和状态文案的圆角框仍是状态网络，不是页面交互总览。交互版先建立完整状态模型，再抽取正文所需子图；其中页面交互总览与局部故事板必须同源于该模型。不要把纯流程节点冒充页面交互总览，也不要把完整状态网络直接压成正文巨图。

需要原型时，再分别判断产品语义是否达到 `interaction_complete` 或 `structure_complete`，以及视觉上下文是已确认设计、现有页面、参考图还是缺失。语义不足时只标注现状或列缺口；已有正式设计时优先复用和增量表达。

### 4. 编译正文与资产

按用户任务聚合入口、信息、动作、反馈、结果和恢复。界面详情优先使用“当前界面或来源证据 → 调整后原型/关键状态 → 就近交互规则”的结构；同构规则改用小表。图已表达的顺序、交接或空间关系不再逐句复述。只要本期改变了页面结构、主操作、可见反馈或关键状态，且上游提供截图/设计稿，就必须复用、裁切或标注相关视觉；没有视觉上下文但语义完整时，至少为核心变化页面生成一张明确标注的低保真结构示意。纯文案、字段或不可见规则变化可以不画图。

复杂原型或截图承接先使用 `assets/prototype-plan-template.json` 记录输入充分度、证据、Surface、复用策略和输出问题，并运行 `scripts/check_prototype_plan.py`。需要标注现状截图时使用 `scripts/annotate_reference_screenshot.py`。

视觉资产的默认生产线（HTML + 无头浏览器截图，见 `scripts/capture_html_png.py`）：

- 产品主流程 / 分支流程：`assets/flow-diagram-template.json` 建模，`scripts/check_flow_diagram.py` 过语义检查，`scripts/render_flow_diagram.py` 渲染 SVG+PNG。不依赖 mermaid-cli / graphviz；`.mmd` 只作为有 mermaid 工具链团队的可选交换格式，不作为渲染路径。
- 关键页面故事板 / 低保真原型：按 `assets/mobile-screen-storyboard-template.json` 用 `scripts/build_screen_html.py` 生成（组件词汇见 `scripts/mobile_screen_kit.py` 头注）。页面必须呈现已决定内容；只有无可用浏览器时才退回 `scripts/render_wireframe_board.py` 灰盒渲染器。

**视觉载体由交付面决定。** 本地交付（Markdown/DOCX/PDF）走上述 PNG 内联。飞书交付时，主流程图和页面交互总览必须发布为**飞书原生画板**，读者可缩放、可追踪；本地 PNG 只作发布前预览与发布审计证据，不把 PNG 贴进飞书正文冒充主交付。画板导入格式按视觉复杂度分工：简洁流程用 mermaid（`scripts/export_flow_mermaid.py` 从 spec 导出）；页面交互总览等精确布局的组合图用纯 SVG（`scripts/render_overview_board.py --svg`，与 HTML/PNG 同源同布局）——飞书画板的 SVG 导入只保留原生 SVG 图元，不支持 foreignObject，所以必须用纯 SVG 发射器而不是把 HTML 包进 SVG。手机屏原型（故事板/关键页面）继续用图片，因为画板承载手机壳组件会损失保真。详见 `references/飞书发布与渲染.md`。

多页面、多分支的交互版默认规划一张“页面交互总览”：页面或关键页面状态作为卡片，卡片间连线必须标动作、条件或系统事件；主操作沿统一阅读方向，失败、返回、空态和终态挂在对应分歧点附近。瞬态（加载中/校验中/提交处理中，模型 `visibility=transient`）不是页面，用 `chip` 扁条节点承载，不渲染手机屏；页面卡片的屏幕内容通过 `screen_source` + `screen_ref` 与需求详情的故事板同源引用，不在总览 spec 里另写一份。使用 `assets/page-interaction-overview-template.json` 建立页面卡片与状态、连线与迁移的映射，并运行 `scripts/check_page_interaction_overview.py`。渲染使用 `scripts/render_overview_board.py`：主路径自动置顶成一条连续阅读线，分支/异常挂在分歧点下方，外部出口收进右侧出口栏，`layout_group` 渲染为分组底带，线型区分主路径/分支/异常/返回并附图例；自动布局不满意时可用卡片级 `layout` 显式覆盖。若页面总览不能降低理解成本，必须写明原因，不能用一张纯流程图或分散局部图静默替代。

正文内联资产只承载可在文档宽度下阅读的主流程、聚焦故事板或总览局部预览；`delivery_role=zoomable` 的完整页面交互总览/全景不得原样缩进正文冒充可读图。它应作为独立下钻，并在正文提供可读的主流程、分区导览或局部预览。页面交互总览让人看懂页面、状态与跳转，完整全景用于证明底层迁移无遗漏。

### 5. 压缩与分层

全文回读并删除：

- 同一结论在概述、详情、规则和验收中的重复扩写；
- 仅用于作者工作的来源 IDs、检查过程和生成术语；
- 不改变协作判断的实现细节；
- 空章节、模板注释、装饰性图表和页面画廊。

再做一次“去规格化”检查：正文中的 FR/RULE/AC ID、URL、query 参数、HTTP 状态码、Node/队列/缓存等实现词，若不影响用户判断或协作责任，一律删除或移到正式 PRD / 研发 spec 下钻。验收只保留主路径、关键限制和高风险恢复，不复制全量 AC。

保留信息不是保留篇幅。每个模块只留下读者完成第一次评审所需的信息，完整规格通过正式 PRD 下钻。

### 6. 验证与发布

| 级别 | 适用情况 | 必须完成 |
|---|---|---|
| 基础 | 所有交付 | 主源抽查、传统骨架检查、作者连续阅读、查看实际资产 |
| 增强 | 视觉版、交互版或多个关联资产 | 执行包/交互模型、跨产物一致性、严格阅读检查 |
| 严格 | 重要评审、重复发布或用户明确要求审计 | 结构化证据、无上下文读者测试、平台发布审计 |

用户要求飞书时，飞书文档是唯一主交付面，本地 Markdown、XML 和图源只是构建材料。发布后回读正文，并逐个查看本轮新增或修改的画板/图片在正文宽度和放大视图中的表现。

## 默认输出

- 一份符合传统 PRD 语义、按需求裁剪的主文档；
- 视觉版/交互版中回答独立问题的必要图形与局部原型；
- 多页面交互版中一张可追踪的页面交互总览，除非有明确且可审查的不适用理由；
- 正式 PRD 的稳定下钻入口；
- 只有用户要求时才展示内部执行包、覆盖报告或审计日志。

## 完成标准

- 非作者能连续回答为什么做、目标是什么、做什么与不做什么、用户怎样到达结果、哪些条件改变结果；
- 第一屏建立背景、问题与目标，而不是生成说明、方案口号或研发术语；
- 正文简洁但不缺入口、信息、动作、反馈、状态、异常和恢复；
- 图、表、原型和文字各自解决独立问题，局部图与对应规则相邻；
- 页面交互总览能从入口沿页面卡片和带语义连线追到主结果、异常、返回与外部出口，不依赖分散详情拼接；
- 交互模型完整不等于正文巨图；展示资产在最终平台缩放后仍清楚；
- 原型深度与上游语义、设计资产和截图证据相匹配，没有把观察或推断升级为产品规则；
- 已完成与风险和平台匹配的新鲜检查，不依赖作者口头补充核心事实。
